# 测试判断、自动化、协作与流程

判断标准和测试方法见 `../references/verification.md`，协作原则见 `../references/discipline.md`。这里只记具体的坑。

## 坑

### 把"跑起来了"当成"能用了"
标记：【高频】
- 现象：显示"通过"只是影子缓冲有图或 vblank 在走；蓝牙"通过"只是 `hci0 up`，从没扫描过；相机脚本能取帧就关闭了"相机不可用"；服务 active、probe 成功、QEMU 通过都被写成功能通过。
- 怎么解决：功能通过必须是用户能感知的结果（看到、听到、摸到、连上），或等价的硬件判据，并与人眼确认分开记录；用户报告的问题，要在用户实际使用的入口验证通过才关闭。
- 适用范围：通用。

### 离线检查全绿，被当成"接近交付"
标记：【高频】【耗时】
- 现象：几十个离线检查、重复构建比对、QEMU 全部通过，候选被叫"最终版"；上机后本版新增的功能全部失败。
- 原因：时间花在容易产生通过记录的检查上，而不是最能否定方案的真机证据上；模拟数据用了虚构的地址和换行符；模拟数据和被测代码基于同一个错误假设。
- 怎么解决：只有离线证据的写"离线通过"；先做能阻止错误上机的必要检查（镜像身份、分区、回程），然后尽早拿最能否定方案的真机证据（内存镜像上机），不要让重复的离线检查拖延它；测试数据至少保存一份真机原文。
- 适用范围：通用。

### 运行中切换测试代替冷启动测试
标记：【高频】【致命】
- 现象：开关调试通道、改 socket 在运行中测试都正常，正式版冷启动卡 90 秒或通道完全不起来。
- 怎么解决：改 unit、socket、udev、initramfs、生成器、启动参数后，用"改动已经生效的镜像"冷启动验证，并先用旧版本复现问题作对照；发布前列出自上次真机验证后改过启动路径的包，每个都要有冷启动记录。
- 适用范围：通用。

### 用户到场后才发现脚本没空跑、前提没查
标记：【高频】【耗时】
- 现象：用户按约定到场，脚本因为一个没读过的电量守卫中止；记录器漏掉了要等的事件；指令来回改；用户比你先发现新版本的回归。
- 原因：每次只补一条针对那次症状的规则（问清有几个充电器、会话不要转发……），没有覆盖共同的根因：交给用户的每一步，都没有先由你在真机上按同一顺序跑过；检查点放在"怎么测"，失误却发生在"把方案交给用户"那一刻。
- 怎么解决：交给用户之前，先在真机上空跑能自动执行的部分（编排、守卫、取证、恢复），能读到的前提由脚本读；逐项问能不能改成软件判据、后台取证或合并，只留非人不可的动作；给一条不带条件分支、写明起止时刻的顺序。见 `../references/discipline.md` 第 7 节。
- 适用范围：通用。

### 把执行者的方案和结论原样转给用户
标记：【高频】
- 现象：执行者给出一份要用户在设备旁待几个小时、动手很多次的在场方案，被原样转交；执行者判断"原厂没有这样做"，结果原厂源码里恰好就这样做。
- 原因：思考被外包了，负责人成了传话的中间层。执行者常沿着任务书给的框架做满，不会回头质疑框架本身。
- 怎么解决：从第一性原理重想一遍哪一步非人不可（常常只剩一个物理动作，其余都能用源码、软件判据或日常使用覆盖）；给用户的话由你自己写、逐项写出你的判断；执行者关于原厂、上游的关键结论，打开源码核一次再用。
- 适用范围：通用。

### 任务书写了测试清单，执行者照单做满
标记：【高频】【耗时】
- 现象：额度和时间大量花在多轮跑分、海量自测、固定的 A/B 轮次上，产出很少；一个只要一两分钟的一致性测试，到很多轮之后才发现大量新增失败。
- 原因：任务书越具体，执行者越照单做满；每个续任务都重新拿一份预算；任务书里亲手写的数字（报告行数、检查间隔）是同一个错误的另一种形式。
- 怎么解决：任务书写要回答的决定、证据门槛、约束和预算；必要的安全步骤和精度要求照写，其余不写步骤、数量和轮次；预算按决定累计；先跑最便宜、最能否定方案的正确性测试，再看性能；长任务开工前逐项问"这一项会改变哪个决定"。
- 适用范围：通用。

### 主机端脚本的问题浪费了真机机会
标记：【高频】
- 常见形式：写死主机 IP（DHCP 实际给的是别的地址）；只模拟了 LF 换行而真机是 CRLF；USB 断开不保证 TCP 收到 FIN，旧连接 90 秒没有 EOF 被当成设备还在线；shell 回显里包含结束标记导致提前截断；`fastboot boot | tee` 返回的是 tee 的退出码；读回命令丢了 stderr 得到空输入的哈希（`e3b0c442…`）；BusyBox 行编辑最多 1023 字节；提示符后跟 `\x1b[6n`；`nmcli -t` 在 pty 下带颜色码；设备重新枚举后主机 fastboot 挂住（解绑重绑 USB 端口可恢复）；Fastboot 刚交接时轮询撞上 ABL 拆 USB 窗口误发命令。
- 怎么解决：用户到场前在真机上完整跑一遍主机侧检查（USB 接口、地址、路由、Fastboot 身份、换行符、命令长度）；用明确的开始和结束标记界定每条命令的输出；Bash 管道开 `set -o pipefail`，需要分开判断时立即保存 `PIPESTATUS`；读回同时核对退出码、字节数和哈希，空输入哈希当失败；EOF 不当成功；同类主机错误第二次出现时扫一遍所有入口。
- 适用范围：通用。

### 测试工具自己制造误判
标记：【高频】
- 常见形式：
  - 显示提交线程短暂的 D 状态被当成挂死（要同一等待点持续几十秒无进展，或内核报 hung task）。
  - 按行数取 dmesg 增量，被环形缓冲覆盖后得到空结果，整轮作废（用 journal cursor 或 dmesg 序号做游标）。
  - 截图快门音拉起音频流，让功耗和电源域的判读失真（功耗测试期间不截图或关快门音）。
  - 可选外设不在时的节点状态（例如没插笔时笔的电池 `present=0`）被当成故障。
  - 主机风扇全速时麦克风判据失败（测之前关主机散热增强，记录风扇状态）。
  - 单帧取样的相机测试拿到黑帧（取连续多帧再判）。
  - 编排器异常被记成通过；测试包装器把失败报成成功；探针杀掉了自己的负载后判失败；采集在开机后太早，把"仍在启动"误报为失败。
  - 诊断模块里的协议常量写错（例如位号对错），那一项"排除"就是无效的。
- 怎么解决：最早出错的层可能是工具本身；编排器异常一律判失败并保存堆栈；每个检查准备一个应该失败的输入；诊断代码的协议常量逐个对到原厂源码；修好工具后，原始数据完整又没被工具影响时，对已保存的证据离线重新判断，不放宽标准；数据缺失或被采集改变时，只重采受影响的部分，并撤回撑不住的旧结论。
- 适用范围：通用。

### 用户测试窗口太短，或没提前通知
- 现象：30 秒的按键窗口过去了用户才知道；结果记成"失败"。
- 怎么解决：需要用户动作时提前通知，说明要做什么和观察什么；能用长时间记录器（例如运行数小时的 evdev 记录）代替窗口的就用记录器；用户报告的物理结果直接记录，与机器证据分开。
- 适用范围：通用。

### 两个任务同时操作同一台设备
标记：【高频】
- 现象：别的任务重启设备，污染了实验；一次"USB 重连成功"其实来自另一个任务的重启；一次只读的状态查询 SSH 让放电守卫判成"有人在用"，整轮运行中止。
- 原因：单一驱动者只是文字约定；只读 SSH 登录也会经 pam_systemd 建一个会话。
- 怎么解决：开始前在交接页写明谁在驱动、到何时，结束时删掉；驱动权由上一个驱动者停掉自己的任务后明确交回才转移，登记过期或进程匹配为空不等于空闲。别人在驱动时不登录那台设备，要看进度读驱动者拷回主机的文件。每份证据绑定启动 ID。能做成锁文件，所有设备工具先检查，就比文字约定可靠。
- 适用范围：通用。

### 主机连不上，就判定设备硬挂
标记：【耗时】
- 现象：主机看不到 USB 重新枚举，于是请用户长按电源键；其实屏幕和触控一直正常。
- 原因：主机通道只是一个信号；回退定时器又是启动后经 SSH 安装的，SSH 不通时根本不存在。
- 怎么解决：判定挂死要第二个独立信号；回程机制随镜像生效（命令行标记 + 已装系统里的单元 + 内建硬件看门狗），见 `../references/verification.md`。
- 适用范围：通用。

### 长时间监视器随执行者的会话一起退出
- 现象：一个要跑几小时的主机监视器中途停了，等待方只按关键字等，没发现日志不再更新，通知晚了几个小时。
- 原因：执行者会话卸载时，它这一轮启动的主机子进程会被一起杀掉。
- 怎么解决：要活过一轮的主机进程交给生命周期明确的进程管理器（例如 `systemd-run --user`），并验证会话结束后它还在（`setsid` 只脱离进程组，逃不出按 cgroup 的清理）；设备一侧用自主运行的 systemd 单元；等周期采样的日志时同时看修改时间，停更超过几个采样周期就去查写者的进程状态。
- 适用范围：通用。

### 同样的失败第二次出现，还在修末端症状
标记：【高频】【耗时】
- 现象：同一类失败反复出现，每次都在末端补一个修复（例如在协议层修一个其实是供电问题的超时）；这是最常见的大块时间损失。
- 怎么解决：停下来，从物理层往上逐层找最早出错的地方：供电和时钟、总线电平、协议、驱动、用户态所有权、输出、观测手段本身；写下已排除的假设和下一个能证伪的实验。
- 适用范围：通用。

### 在已经挂死的启动里做"排除"实验
- 现象：多轮对照全部"无效"，错误结论被写进了代码注释或文档。
- 怎么解决：排除实验从干净的基线开始：已经出过故障、又不能证明局部复位能恢复基线时，从新启动开始，并记录开机时长。
- 适用范围：通用。

### 判定"这个改动没用"太早
- 原因：同时存在另一个错误，正确的修复也表现为无效。
- 怎么解决：判定无效前说明其他条件为什么都对；说不清时写"在当前未知条件下没有看到改善"。
- 适用范围：通用。

### 用一个数据点编出根因
标记：【高频】
- 常见形式：一次失败就归因于某个显眼的属性（例如镜像大小），换一个变量再测就被推翻；用休眠中不走的时钟算睡眠时长，得出"自醒"；在暗场景或特殊负载下判断显示缺陷，对照组其实一样；拿来对比的两组读数其实不只差被怀疑的那一项。错误结论一旦交给执行者去"修"，浪费会成倍增加。
- 怎么解决：报告根因之前，用第二个数据点或一个对照组试着推翻它；比较两组读数前，先确认它们只差被怀疑的那一项；测量方式本身要先确认可信（时钟源、光照、场景）。要公开的结论，先让一个不带先入之见的审查者对照原始数据过一遍。
- 适用范围：通用。

### 偶发问题没复现就放过
- 现象：一个偶发故障几轮没再出现，就被当成已经好了；之后在用户手里复现。
- 怎么解决：找一个能确定复现的子问题，或人为放大竞态窗口，把概率性问题变成确定的实验；修复在同样的放大条件下验证。见 `../references/verification.md` 的测试方法。
- 适用范围：通用。

### 结论在上下文压缩或换人后丢失，同一个错误被重新引入
- 怎么解决：否定过的方案和撤销过的改动写进放弃记录；上机前对照。
- 适用范围：通用。

### 已知的坑只在某个 agent 的记忆里，执行者照样踩
标记：【高频】
- 现象：候选内核被直接装进启动槽、启动镜像漏了一步预处理、无人值守时卸载了真实硬件驱动——相应的规则其实早就写在经验库或某个 agent 的私有记忆里。
- 原因：执行者只读规则文件和任务书，看不到这些地方；规则写下了，但没有出现在执行者做事的那一刻。
- 怎么解决：设备和工具的坑写进所有执行者都会读的仓库文档，设备任务书引用它；同类失误第二次出现，把检查做进工具、模板或守卫（例如构建脚本拒绝身份不符的设备树、刷写脚本拒绝零填充镜像），不再加一条更窄的文字规则。
- 适用范围：通用。

### 用提问代替测量
- 现象：等用户回答一个问题等了几个小时，而这个问题本来可以用只读的远程诊断手段直接测出来。
- 怎么解决：能自己测的先测；需要用户判断之前，先测能拿到的参照（例如原厂 Android 在同样条件下的表现）。
- 适用范围：通用。

### 复用调研按项目名找，漏掉了现成的实现
标记：【高频】【耗时】
- 现象：自己设计的流程踩了同类项目早已解决的问题；快要发布时才发现，已经导入过代码的同一位作者另有一个更完整的仓库。
- 原因：只按已知的项目名搜；调研放在设计之后。
- 怎么解决：按接口词搜，列出已跟踪作者的全部仓库，查 fork 网络和其他平台；定设计前做，而不是做完再补。见 `../references/decisions.md` 第 1 节。
- 适用范围：通用。

### 测试被桌面的自动行为或残留状态干扰
- 现象：背光寄存器检查失败，其实是 GNOME 自动亮度改写了值；GUI 测试在没有会话环境的 shell 里启动应用失败；一个测试留下的睡眠抑制器让设备从安装起就没深睡过，一个"只在全新安装出现"的问题因此被误判成安装路径问题。
- 怎么解决：测试前关掉会干扰的自动行为、测试后恢复；GUI 测试从会话里取环境（`systemctl --user show-environment`）或用桌面自动化工具启动；测完让测试机回到和用户机一致（删临时单元、抑制器、暂存模块、测试工具留在 `/var/crash` 的崩溃报告，恢复登录界面和自动登录状态）。
- 适用范围：GNOME；2026。
