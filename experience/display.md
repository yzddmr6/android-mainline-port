# 显示

## 推荐路线

屏幕点亮有两种方式，先理解差别再选：

| | 借用固件画面（simple-framebuffer + simpledrm） | 原生接管（DPU + DSI + 面板驱动） |
|---|---|---|
| 原理 | bootloader 已点亮面板并让显示控制器循环扫描一块内存，Linux 只往这块内存画图 | 内核的显示驱动重新初始化控制器和接口，面板驱动重新发上电命令 |
| 首次出图 | 快（一两天） | 有现成面板驱动时几天；自写面板驱动可能一到两周 |
| 能力 | 没有亮度调节、真正熄屏、刷新率切换、外接显示、休眠前提；GNOME 看到的连接器类型是 Unknown | 全部具备 |
| 主要风险 | 资源回收（见 `kernel-and-resources.md`） | 参数错误导致花屏、熄屏亮屏生命周期 |

**建议**：上游显示驱动支持这个 SoC、面板驱动可以从社区或厂商代码拿到时，直接原生接管。否则先借用画面打通安装链路和桌面，**同时**开始原生接管；不要在借用画面上做亮度、熄屏之类的产品修补。

### 原生接管的步骤

1. 在原厂系统用原厂驱动的 debugfs 保存"黄金快照"：时钟树、管线拓扑（mixer、DSC、接口数量）、DSC 参数、PHY 时序、面板上电命令。不要用 `/dev/mem` 扫描显示寄存器。
2. 面板驱动：优先复用社区或上游现成的；上电命令从厂商 dtsi 机械提取，与本机原厂设备树逐条核对。
3. 先用模块方式加载显示驱动（`msm` 做成 `=m`，启动时不加载，调试通道起来后手动 `modprobe`），这样挂死前能拿到日志。
4. 把显示子系统加入 SMMU 的直通（identity）列表，让固件画面能撑到驱动复位那一刻（上游对部分 SoC 已有先例）。
5. 先在固件当前的刷新率下完成接管，再做其他刷新率。
6. 验收后再做熄屏、亮屏、背光关联、DPMS。

## 完成标准

- 人眼看到正确画面（首次必须）。
- 硬件指标：显示接口帧计数按刷新率增长；没有欠载（underrun）和 DSI 错误；原生接管时 debugfs 里的拓扑与黄金快照一致、CRTC CRC 稳定、面板状态寄存器读回正常（例如 DCS `0x0A`）；借用画面时显存区域采样有多种颜色、显示总线互连每一跳都有投票。每个指标写明测点在哪：CRC 在 DSI 和面板之前，vblank 只证明控制器在扫描，DCS 错误计数只覆盖面板实现了、而且读回有效的那几类错误（短读不能当成零）。
- 多次冷启动都满足时间预算；熄屏再亮屏多轮后画面和触控都恢复。
- 不算通过：进程在运行、`/dev/fb0` 能写、显存里有图、connector 状态 connected、vblank 计数对得上目标刷新率。每个新模式和模式间的切换都要目视一次。

## 坑

### 把借用固件画面当成产品路线
标记：【高频】【耗时】
- 现象：桌面能用，但没有亮度条，熄屏只是黑画面背光常亮，设置里刷新率显示 60 Hz，挂起和外接显示没有前提；为维持它又花数天处理资源回收。
- 原因：simpledrm 只拥有一块内存，不管硬件；GNOME 对 Unknown 连接器不提供内屏功能。
- 怎么解决：借用画面只用于首次点亮和打通安装链路，原生接管尽早并行开始。
- 适用范围：通用；2026。

### 软件状态全部正常，屏幕却是黑的，被误判为"已点亮"
标记：【高频】【耗时】
- 现象：connector、fb0、fbcon、背光寄存器全部正常，用户看到纯黑；甚至得出"面板坏了"的错误结论。
- 原因（常见叠加）：背光芯片的总使能寄存器从未写（主线把它当只读 ID）；DSC 视频模式面板用了非连续时钟导致失锁；TE 引脚没接导致 vblank 超时；DSC 参数与面板解码器不一致；接口有效宽度取整不一致；面板供电电压不在 PMIC 步进上导致整颗 PMIC 消失。
- 怎么确认：LCD 全黑先查背光（独立背光芯片可以单独验证；OLED 没有背光）；把厂商显示驱动源码逐项对完再做黑盒二分。
- 怎么解决：按厂商实现修正每一项。
- 提前预防："点亮"只由人眼或面板侧硬件指标判断。
- 适用范围：通用；2026。

### DSC 参数不一致：条纹、花屏、彩条却能通过
标记：【高频】【耗时】
- 现象：画面有横向条纹或块状错误；纯色彩条看起来正常。
- 原因：DSC 码率控制（RC）参数表版本（1.1 与 1.2）、`first_line_bpg_offset`、`initial_lines`、slice 宽度取整、`slice_per_pkt` 与面板解码器不一致；主线驱动可能用自己的默认 RC 值覆盖面板驱动提供的值。
- 怎么确认：用跨 slice 的压力图测试（彩条在 RC 错误时也能通过）；把派生值与面板的 PPS 数据逐字段对比。
- 怎么解决：按面板（厂商）实际值设置，确认驱动没有覆盖。
- 适用范围：高通 DPU + DSC 面板；2026。

### 管线拓扑选错：零报错但全屏花屏
标记：【耗时】
- 现象：所有组件 active、PPS 已发、无错误，画面是花的；多轮"单变量调参"都无效。
- 原因：拓扑选了 4 个 mixer，而非虚拟平面只能喂 2 个，另一半是垃圾数据，压缩器把垃圾正常编码。
- 怎么确认：先看 `/sys/kernel/debug/dri/0/state` 里的 `mixer=`、`dsc=`、`stage=`，与厂商拓扑对比。
- 怎么解决：没有虚拟平面时不选四路拓扑。
- 提前预防：拓扑错的时候，其他正确的修复（例如 `slice_per_pkt`）也会表现为"无效"。判定某改动无效前先确认其他维度正确。
- 适用范围：高通 DPU；2026。

### 模式校验拒绝高刷新率，或可用模式数为 0
- 现象：`MODE_CLOCK_HIGH`；连接器 0 个模式；某个刷新率（例如 144 Hz）不可选，而社区版本可以。
- 原因：模式校验用 bootloader 残留的时钟作为上限；或按分辨率算出的显示核心时钟略高于 SoC 上限（例如需要 577 MHz，上限 575 MHz）。社区可能直接改掉了这条检查。
- 怎么解决：上限用驱动可达的最高频率而非残留值；高刷新率先在固件默认刷新率下完成接管，再评估考虑 DSC 压缩后真实带宽的修正。不要为了通过校验把时钟抬到 OPP 表之外（会导致 `-ERANGE` 和投票丢失）。
- 适用范围：高通 DPU；2026。

### 只启用显示子系统节点、没有任何组件时，显示驱动空指针
- 现象：启用 MDSS/DPU 节点后启动早期挂死，没有 USB。
- 原因：DPU 没有任何组件时把空列表交给 component 框架，空指针。
- 怎么解决：无组件时返回 `-ENODEV`（上游级一行修复）；显示驱动先做成模块手动加载就能拿到 oops。
- 适用范围：主线 msm 驱动；2026。

### 启用显示子系统节点后，固件画面立刻损坏
- 现象：驱动还没复位硬件，画面就已经花了。
- 原因：SMMU 在启动早期把显示流接到新的地址域，固件扫描的内存开始缺页。
- 怎么解决：把该 SoC 的显示子系统 compatible 加进 SMMU 的 identity 域列表。
- 适用范围：高通；2026。

### 熄屏后再亮屏失败
标记：【高频】【耗时】
- 现象：亮屏后 DSI 命令 DMA `-110`、`CTL_FLUSH` 卡住、频繁 vblank timeout 花屏，或 `dsi_err_worker status=4`；静止登录界面测试却"通过"。
- 原因（已确认的一例）：显示电源域掉电前缺少 VBIF AXI halt 握手；CTL 软复位永不完成，需要 override；恢复时先开时钟后投票。
- 怎么确认：逐项对照原厂驱动的 power-event 钩子；每次对照实验从干净的新启动开始，在已经挂死的启动里做"排除"实验没有意义。
- 怎么解决：按原厂顺序补握手和复位；恢复时先投票再开时钟。
- 提前预防：显示验收必须注入新帧（移动鼠标或打开窗口），commit 和 vblank timeout 一律判失败。
- 适用范围：高通 DPU；2026。

### 接管时屏幕会黑一下
- 现象：原生驱动加载时画面消失约 1 秒。
- 原因：上游没有无缝接管，驱动通过 aperture 移除 simpledrm 后复位硬件。
- 怎么解决：属于正常现象，文档里说明即可。
- 适用范围：主线；2026。

### GNOME 测试清理代码把登录区移出屏幕
- 现象：软件全绿但用户看到全黑或没有登录框。
- 原因：测试脚本调用 `org.gnome.ScreenSaver.SetActive(false)`，gnome-shell 隐藏锁屏时把登录区平移出屏幕。
- 怎么解决：不要调用 `SetActive(false)`；唤醒只发一次无文本按键；调用 GNOME D-Bus 接口前读 gnome-shell 源码确认语义。
- 适用范围：GNOME；2026。

### 系统恢复上次关机时的亮度，开机很暗
- 原因：systemd-backlight 保存并恢复了一个很低的亮度。
- 怎么解决：只在没有有效保存值、或保存值低于合理下限时，在显示管理器之前用一次性服务写默认亮度；保留用户正常的选择，不要用 dconf 锁。
- 适用范围：systemd 系统。

### 多颗背光芯片
- 做法：每颗芯片作为 LED 子设备，用 `led-backlight` 聚合为一个背光设备，并在面板节点里关联，桌面才会给亮度条。
- 适用范围：通用。

### 双 DSI 熄屏花屏、亮屏后副 DSI 首条命令超时
标记：【高频】【耗时】
- 现象：DPMS 关屏瞬间画面花掉、欠载大量增加；或每次亮屏副 DSI 的第一条命令 `-110`，随后 vblank、commit 超时，挂起也跟着失败。
- 原因：共享 CTL 的拆除顺序不对：在停止接口之前就清理了 CTL；先撤主通路会连带撤掉从通路的本地使能，而从通路的像素路径已经解绑，VBIF halt 得不到应答，命令 DMA 卡住；从 DSI PHY 的状态没有保存和恢复。
- 怎么解决：分阶段关闭：确认两路时序引擎都已停止，保留从通路完成必要的提交和停止握手，再复位、清理共享 CTL；导入社区修正的关闭顺序和从 PHY 保存恢复。验收做几十次 DPMS 循环，数欠载事件，并测亮屏后的首条命令。
- 适用范围：高通 DPU 共享 CTL 的双 DSI；2026。

### 部分机器半屏花屏：从 PHY 的初始化写入被引用计数跳过
标记：【耗时】
- 现象：一半屏幕持续或间歇横纹，主机侧错误计数为零，往往只在部分机器（另一家面板、另一批模组）上出现；有时连带集成触控校验失败。
- 原因：共享 PLL 的双 DSI 里，PHY 使能时预置了 bias 引用计数，bias helper 见计数非零就提前返回，从 PHY 必需的寄存器（例如 `PLL_SYSTEM_MUXES`）从未写入；此前的频率回读又可能把它清零。
- 怎么确认：本机不复现时，用原厂的寄存器块整块对照，把怀疑面收敛到具体的写入点，再请受影响的用户做一次可回切的对照；修复后读回从 PHY 寄存器。
- 怎么解决：保留引用计数和锁，只让首次引用解除 shutdown，但每次 bias 使能都恢复必要的 mux 和稳定时间；保留已经证实正确的共享 PLL 拓扑，不必改成两路独立 PLL。
- 适用范围：采用这套共享 PLL/bias 管理的高通 bonded DSI；2026（上游有同题投稿，先核对）。

### 照搬原厂"每次配置一次"的复位，在主线里被调用了很多次
- 现象：显示再次使能后集成触控起不来（停在某个复位状态），可能同时大量欠载；寄存器终态却和原厂一样。
- 原因：原厂每次配置只做一次的模拟/PLL 复位被放进了 `vco_prepare()` 一类的回调；时钟框架的 `CLK_OPS_PARENT_ENABLE` 等机制让一次显示使能里反复调用它。
- 怎么解决：搬之前先确认回调的真实调用频率和硬件生命周期；区分 PHY 模拟复位和链路稳定后只做一次的控制器软复位。寄存器终态相同不等于序列等价。
- 适用范围：把原厂序列搬进 CCF 回调时通用。

### 触控时整屏单帧洗白（显示与触控共用一颗芯片）
标记：【耗时】
- 现象：TDDI 面板上手指按住或滑动时偶发整屏闪一帧，高刷新率下更明显；显示 CRC、DSI 错误、面板错误计数全部正常，链路寄存器逐项对齐原厂也无效。
- 原因：主机每帧用 GPI DMA 读一次触控帧；读线程发起传输后睡下，如果所有 CPU 都空闲，cpuidle 会一路选到系统级最深的低功耗域，DMA 到内存的通路停摆约几毫秒。闪烁与这笔卡在半截的 SPI 事务对应，并随修复在同一次启动里可逆（DDIC 内部为什么因此驱坏一帧是推断，没有数据手册）。
- 怎么确认：用 ftrace 量 SPI 读帧耗时，分布是精确两倍的双峰；抓 `psci_domain_idle_enter` 看慢事务期间进入了哪个状态；用户态打开 `/dev/cpu_dma_latency` 写一个介于簇和系统域退出延迟之间的值，看现象是否消失。
- 怎么解决：在 SPI 控制器驱动里，只在 GPI 消息 prepare 到 unprepare 期间持 `cpu_latency_qos`，数值按本机设备树的空闲状态延迟表取（允许簇休眠、挡住系统域）；读帧间隙照常深睡，不碰屏时功耗不变。不要全局禁用深睡，不要全程持票，不要为对齐而对齐别的寄存器。
- 适用范围：高通 GENI SPI + GPI DMA 读 TDDI 触控帧；2026（未进上游，先核对）。

### 借用画面的启动早期锁存欠载：显示时钟控制器注册时把 RCG 停到了 XO
- 现象：显示时钟控制器内建后，借用画面在它注册的那一刻锁存欠载位。
- 原因：时钟控制器注册时按默认 ops 把 MDP 的 RCG 停到 XO，正在扫描的固件画面瞬间降频。
- 怎么解决：对这类共享 RCG 使用不在初始化时停泊的 ops（上游部分 SoC 已有 `clk_rcg2_shared_no_init_park_ops` 先例）。
- 适用范围：高通 dispcc + 借用画面；2026。

### frame-done 或 pending 超时告警：先分清是记账竞态还是真实故障
- 无害的一种：上游 `dpu_crtc_commit_kickoff()` 在 encoder kickoff 之后才置位定时器，重启后的第一个 vsync 可能先清掉状态，产生记账告警，画面完全正常。需要时按上游顺序修正并保留真实超时的检出能力。
- 真实的一种：共享视频 CTL 的主从 encoder 对同一个 CTL 各 flush 一次，从侧 pending 只增不减，从 INTF 没有对应的 vsync 回调。每次 kickoff 只提交一次，并核对完成回调归属。
- 不能按报错词统一忽略：VBIF halt 失败（见上面的双 DSI 条目）也表现为 pending 和 commit 超时。
- 适用范围：主线 msm；2026。

### 夜灯（色温调节）
- 做法：需要 DSPP 的 GC/GCv2 色彩硬件和对应的编程路径，社区已有实现，按来源导入；GNOME 50 的夜灯不经过 Mutter 空 LUT 的缺陷路径，不必改发行版 Mutter。
- 坑：REGDMA 是一种编程方式，不是必要条件。最早的错误是 `GC2 REGDMA failure ... -110`（例如亮屏的原子提交在 encoder 使能前经 REGDMA 编程伽马，或空 LUT 的"关闭"被编码成极短的 DMA 提交），随后才有 DSI、vblank、`pm_runtime_force_suspend` `-EBUSY` 的连锁失败。空表逐个 DSPP 走 MMIO 旁路，伽马可以走 MMIO；非空表和空表两条路径分别验证（一直加载非空色彩表的机器测不到空表路径）。
- 风险：REGDMA 复位得不到确认时，原实现会无限等待；要给退出加时间上限，并在超时时保留仍被 DMA 使用的映射，不能释放。
- 适用范围：高通 DPU；2026。

### 高刷新率和低刷新率
- 模式校验修正后高刷新率可以稳定工作，但每一档都要连同触控和 DPMS 一起测（见 `touch-and-input.md`）。
- 低刷新率档位 vblank 正常时面板仍可能黑屏，或切回后灰屏：只开放目视验证过的档位，失败后恢复可用模式并核对 `monitors.xml`。
- 适用范围：高通 DPU + DSC 面板；2026。

## 未解决

- 熄屏后再亮屏和休眠唤醒时 `dsi_err_worker status=4`：同一个错误串可能有多个原因，这一例尚未归因。
- 部分 DSC 面板的高刷新率需要更准确的显示核心时钟算法。
- 低刷新率档位面板黑屏的根因（面板侧还是切换链）。
- REGDMA 本身超时的机制：MMIO 旁路有效，REGDMA 的完整修复未知。
