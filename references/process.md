# 详细流程

每一步写：目标、要做的事（按顺序）、产出、完成标准、相关经验。顺序本身就是经验：最大的时间损失大多来自跳步或倒序。

总览：

```
第 0 步  立项：工作区、资料池、复用调研、评估、和用户确认
第 1 步  构建环境：工具链、缓存、能复现社区基线
第 2 步  原厂取证与备份：root、备份、取出"标准答案"
第 3 步  首次启动：摸清 bootloader，内存里跑起 shell 和调试通道
第 4 步  首次点亮与内存桌面：显示、触控、RAM 根、GNOME
第 5 步  安装到存储：分区、根交付、双系统、调试通道、冷启动
第 6 步  外设逐个适配：按优先级，一次一个
第 7 步  打包、全新安装验收、发布
第 8 步  维护：跟上游、还技术债
```

并行原则：第 1 步可以和第 0 步后半段并行；原生显示接管可以从第 4 步开始与其他工作并行；第 6 步的离线准备可以并行。真机始终只有一个操作者；需要归因或第一次碰高风险硬件时单项测试，其余互不干扰的改动可以合成一个候选验证。

---

## 第 0 步：立项

**目标**：搞清能不能做、怎么做、大概多久、哪些事要用户决定。不碰设备。

1. **建工作区**：按 `discipline.md` 建私有工作区、内核仓、集成仓，写 AGENTS.md 初稿，和用户定好提交作者、账号、仓库名、许可证。
2. **核对设备身份**：型号、SoC 精确型号（含后缀）、bootloader 能否解锁、原厂系统版本、存储结构、A/B 结构。
3. **建资料池**：拉取并固定版本（记录地址和提交）：
   - 上游内核对该 SoC 的支持（dtsi、显示、GPU、无线、音频、远端处理器），以及 lore/patchew 上的在审系列。
   - 同 SoC 社区内核和用户态项目（例如 postmarketOS、ROCKNIX、个人维护的分支）。按接口词搜（SoC 代号、驱动名、设备节点、协议名），查已跟踪作者的全部仓库、导入来源的 fork 网络和 GitHub 以外的平台（见 `decisions.md` 第 1 节）。
   - 厂商开源内核：第一天就清点里面有哪些驱动（显示、触控、键盘、功放、充电），列一张"原厂源码对照表"。有源码就不要反汇编。
   - 原厂固件包，校验哈希。
   - 同类设备的已有 Linux 项目：先读它们的安装说明、安装器、复盘和技术债。
4. **复用调研表**：每个功能一行：上游状态、社区状态（真机跑通还是只有代码）、厂商代码、差距、建议来源、复查日期。
5. **硬件清单**：面板、触控、GPU、无线芯片、功放与 codec、电量计、背光、PMIC、传感器、键盘桥、相机、指纹。
6. **技术选型**：按 `decisions.md` 对主要路线做选择，记录理由。
7. **估算工作量**：按 `discipline.md` 的方法给区间和最大的不确定因素。
8. **和用户确认**：把需要用户决定的事一次列出（见 SKILL.md），用提问工具确认。确认后写进 AGENTS.md。

**产出**：工作区、资料池清单、复用调研表、硬件清单、选型记录、评估报告、AGENTS.md。

**完成标准**：用户确认了决策清单。

**相关经验**：`../experience/testing-and-process.md`（没先看同类项目、复用社区先比较地基）。

## 第 1 步：构建环境

**目标**：能快速、可复现地构建内核和根文件系统。

1. 按 `build-environment.md` 装工具链、配置 ccache、规划 OUT 目录和磁盘。
2. **原样构建社区参考设备的内核一次**，证明工具链和基线没问题。之后新代码的失败才能归因。
3. 写内核构建脚本：固定输入、长期 OUT、`flock`、记录构建身份。
4. 决定根文件系统构建方式（原生 ARM64 CI 优先），先跑通一次。
5. 所有超过 5 分钟的步骤加计时。

**完成标准**：参考内核可复现；增量构建一次只需几分钟；根文件系统能构建。

**相关经验**：`../experience/build-and-release.md`。

## 第 2 步：原厂取证与备份

**目标**：拿到恢复能力和所有"标准答案"。之后的持久写入都以此为前提。

1. **只读接入**：核对 serial、型号、解锁状态、当前槽位、电量。线材有问题时 Fastboot 可能不出现。
2. **取得 root**：先确认解锁会不会清数据、手上有没有同版本的原厂镜像；再直接 root 原厂系统（按启动布局和 root 工具的安装模式修改 init_boot 或 boot），或临时 `fastboot boot` 一个带 root 的 recovery。不要在原厂内核上拼最小探针。
3. **备份**：按用户确认的范围逐分区备份（通常排除 userdata 和 super，写明没备份的部分靠什么恢复，例如官方完整包），另存每个 LUN 的主备 GPT。主机和设备两侧算哈希，一致才算完成；哈希只证明复制一致，恢复所需的分区和本机数据是否齐全另外核对。记录清单（盘符会变，以后只按清单解释）。
4. **取证**（趁原厂系统在）：
   - 运行时设备树 `/sys/firmware/fdt`。
   - 启动分区镜像头、vbmeta 信息、`fastboot getvar all`、bootloader 支持的只读诊断命令。
   - 原厂能力清单：硬件与子系统、所选设备树变体、内核模块、固件文件及哈希、HAL 实现与声明、init 服务、权限 feature 和编解码声明。绑定原厂版本和来源；多机型 ROM 的文件存在不等于本机实装，兼容性要求也不等于已实现能力。
   - PMIC 电压寄存器实际值、常开电源列表。
   - 显示：原厂驱动 debugfs 的时钟、拓扑、DSC 参数、面板命令（不要用 `/dev/mem` 扫描）。
   - 原厂日志里的命令序列：触控固件下载、功放初始化、无线驱动初始化（含功率上限）、充电协商。
   - 本机唯一数据的位置：校准、MAC、蓝牙地址、传感器配置。只记位置，内容放 `private/`。
5. **恢复演练**：确认恢复镜像、进入 Fastboot 的按键、恢复步骤。

能力清单作为后续完成度的基线：每项映射 Linux 的内核/设备树、固件、权限、运行库、应用入口和当前状态，附可核对的结果与最早缺口；未知、明确不适用、有意暂缓分别保留，不能只列已经能用的功能。每版从这些空白处按日用价值和实现成本排优先级，子系统 running、节点存在或一个消费者成功都不能让整组能力变成通过。固件选择方法见 `../experience/kernel-and-resources.md`。

**产出**：已校验的备份和清单、取证文件、恢复说明。

**完成标准**：备份校验一致；恢复镜像在手。

**相关经验**：`../experience/usb-and-storage.md`（备份、盘符）、`../experience/bootloader-and-boot.md`（原厂探针）。

## 第 3 步：首次启动

**目标**：主线内核在内存里跑起来，主机能连上 shell，超时自动回原系统。

1. **离线搞清 bootloader**：镜像格式、设备树叠加（libufdt 加正对照）、命令行来源和长度、根 compatible 改写、hypervisor 节点。
2. **最小板级 DTS**：PMIC、存储、USB（设备模式）、按键、ramoops、simple-framebuffer（如果走借用画面）。数值全部来自第 2 步的取证。
3. **bootloader 强制叠加 dtbo 时**，打包期注入符号表到 disabled 容器（先离线复现叠加，见 `../experience/bootloader-and-boot.md`）。
4. **最小 initramfs**：块设备只读并复核、USB NCM、DHCP、telnet/SSH、计时退出、充电模式分支。调试通道建立前不碰外设寄存器。
5. **时标探针上机**：证明交接、运行时长、自动恢复。
6. **加 shell 和通道上机**。
7. **首启检查清单**：根 compatible、`systemd-detect-virt`、最终 `.config`、`devices_deferred`、sync_state 状态。

**完成标准**：双向命令、能取 dmesg、超时回原系统；启动格式写成文档。

**相关经验**：`../experience/bootloader-and-boot.md`、`../experience/kernel-and-resources.md`。

---

## 第 4 步：首次点亮与内存桌面

**目标**：在内存里跑起完整桌面，人眼看到画面、手指能操作。

1. **选显示路线**（见 `../experience/display.md`）：能原生就原生；否则借用画面，并在设备树声明固件在用的资源、提供者内建。
2. **原生接管并行开始**：即使先借用画面，也从这里开始准备原生显示（黄金快照、面板驱动、模块化加载）。
3. **触控**：TDDI 一开始就接入面板电源序列。
4. **RAM 根**：官方根 SquashFS + OverlayFS，HTTP 经 USB 网络传入。
5. **桌面**：GDM、GNOME 会话；临时自动登录只在这一阶段用。
6. **建桌面自动化工具**：截图、输入注入（见 `verification.md`），之后的桌面测试不再依赖用户。
7. **加验收预算脚本**：时间、带宽、显示硬件指标，多次冷启动看。

**完成标准**：人眼确认画面、手指确认触控；硬件指标通过；超时回原系统。

**相关经验**：`../experience/display.md`、`../experience/touch-and-input.md`、`../experience/kernel-and-resources.md`。

## 第 5 步：安装到存储

**目标**：持久安装，冷启动可用；双系统时来回切换可用。桌面在内存里能跑之后就做，不要等外设做全。

1. **确认分区方案**（用户已在第 0 步选过）。
2. **做维护镜像**：内存里运行、带存储驱动、root shell、分区工具、不挂载分区、无会话超时自动回 Fastboot。
3. **写分区表**：用维护镜像，先备份 GPT，写后读回，`sgdisk --verify`。
4. **根文件系统交付**：设备上格式化 + 解压 tar；预置本机唯一数据（校准、地址），让首启时触控、蓝牙可用。
5. **启动镜像集**：按本机实测格式生成，写入活动槽，读回校验；保存 Android 镜像集和上一版 Linux 镜像集。
6. 双系统时：**系统内切换工具**和 Android 侧切换入口（例如 root 模块）；开机标记槽成功的服务。
7. **调试通道**：默认关闭、可显式打开；首次刷入测试机前先打开并确认有退路。
8. **冷启动验收**；双系统时 Linux → Android → Linux 来回各一次。
9. 内核更新路径：在设备上装新内核包，钩子重建启动镜像集，保留回滚集。日常迭代走这条路，不重刷根。

**完成标准**：冷启动预算通过；双向切换真机通过；调试通道冷启动可用（关闭时确实不可用）。

**相关经验**：`../experience/usb-and-storage.md`、`../experience/ubuntu-userspace.md`、`ubuntu.md`。

## 第 6 步：外设逐个适配

**目标**：按优先级把外设做到日用。

建议顺序（按用户需要调整）：Wi-Fi → 音频（扬声器、麦克风）→ 电量与充电 → 按键与熄屏 → GPU 加速 → 蓝牙 → 原生显示（亮度、熄屏）→ 自动旋转 → 键盘配件 → 休眠 → 视频硬解 → USB 主机与外接显示 → 相机等。

每个外设的循环：
1. 读 `../experience/<领域>.md` 的推荐路线和标记条目。
2. 查复用：上游、社区、厂商源码；记录来源。
3. 对照原厂取证，写下最早可能出错的层和判据。
4. 离线构建内存测试镜像。同一版本里互不干扰的改动可以合成一个候选一次上机，需要归因或第一次碰高风险硬件时只改这一项。对已安装的系统测候选内核时，不要直接装包（钩子会写槽），按 `../experience/bootloader-and-boot.md` 的方法暂存模块、在设备上生成 initramfs、RAM 启动。
5. 真机测试：机器判据 + 必要的物理确认；失败按层定位；同类失败第二次出现就停下来写分析。
6. 通过后合并进主线版本，升 ABI 打包，装到设备，冷启动回归。
7. 写设备侧自检，加入每次构建后的回归。
8. 为了快速跑通用的临时做法，登记进技术债。

**完成标准**：每个外设都有真实结果证据，并通过冷启动回归。

## 第 7 步：打包、全新安装验收、发布

1. **功能冻结**：发布前不再加新功能。
2. **打包**：按 `ubuntu.md` 的分层拆包；原生 APT 安装、升级、卸载都通过。
3. **构建发布物**：从干净提交、固定输入构建；只编码已用块或用 tar；附件精简。新功能的生命周期先用可替换的包或 RAM 启动验证过，再组装正式发布物，不要过早组装、反复重做。
4. **最终候选的完整回归**：覆盖启动预算、显示与触控生命周期、各子系统、挂起（插电和电池）、升级路径；之后候选再变时按影响补测。结果与上一版对比，退步立即标出。
5. **全新安装验收**：严格按公开文档在真机上从零装一遍，包括 GNOME 首次设置向导（用户用手指走完）；然后冷启动验收、双向切换。文档写错或缺步骤，就是这次要找的问题。
6. **普通用户第一小时审计**：语言、键盘、时区、缩放、联网、浏览器、音量、亮度、电源键、主机名、apt 是否可用。
7. **对外文档审核**：主 agent 亲自审 README、安装、升级文档和发布说明，去掉内部代号、内核 ABI 号、实验编号、哈希堆砌；支持表只写支持程度（能用、缺什么），不写"待验证"一类的核验状态；首版不做的写"不支持"；首页给"让 AI 帮你安装"的提示词；写清风险（可能变砖、清数据）。用一个脚本扫描推送范围里的内部代号和核验字眼，命中逐条处理，再逐文件看一遍。
8. **发布**：推送、打标签、上传附件、核对附件名称大小和校验和。推送和公开前问用户。

**完成标准**：别人按文档能构建、安装、用起来。

**相关经验**：`../experience/build-and-release.md`、`../experience/ubuntu-userspace.md`。

## 版本节奏

第 6、7 步按版本循环：每个版本先在路线文档里写定范围和每项的验收方式，开发完成后集中测试（需要用户参与的放到最后一次），收尾发布，清理分支、worktree 和旧产物，然后再开下一版。不要在一个版本没发布时继续堆新功能。每次定范围之前做一次社区复查。

## 第 8 步：维护

- 上游合入某项功能后，换成上游版本并删除本地实现。
- 定期过一遍技术债表，按影响排序还债。
- 每次内核或启动相关更新都冷启动验证。
- 每个版本审一次社区 PR（见 `decisions.md` 的"接收社区贡献"）。
- 新踩的坑写回本 skill 的 `experience/`（如果你在维护这个 skill）。

### 内核换代

跨大版本换代、或把几台设备合到同一棵内核时（决策见 `decisions.md` 的"内核换代与多设备共用内核"）：

1. **离线**：固定旧产品发布提交、其上游基线和新树提交，取 `Δ旧 = diff(上游基线, 旧产品)`，逐项核对新树是否保留行为。清单覆盖新增、修改、删除、重命名及纯删除的文件/补丁，不只搜新增行或看提交是否是祖先；驱动、DTS、Kconfig、Makefile 和配置片段一起核对。每项判为已迁入、上游等价、明确不迁或待处理，指向新实现及成立条件；没有依据的缺行按潜在误删处理。上游改名或重构时查历史与运行时条件，不能机械补回旧行。
   - 设备树另比最终 DTB 的节点和属性，将 phandle 解析为节点路径后比较，避免编号或源码挪位造成误报。每台产品分别保留清单；只查过几个子系统不能宣称全部改动已带齐。缺行清单通过只允许进入 RAM 验证，不代替功能验收。
2. **首次受控 RAM 启动**：带挂死即重启的参数和随镜像生效的回程；起来后先比对同一台机器新旧内核开机日志的探测与服务差异，把缺失的先补齐。
3. **验收**：覆盖用户可见项（电量与图标、声音、显示、触控、相机、挂起实睡时长与唤醒源、无线），截图亲自看；之后才持久安装。
4. 旧内核线保留到新线发布并稳定之后。
