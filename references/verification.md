# 怎么判断"通过"

## 状态词

| 状态 | 含义 | 需要的记录 |
|---|---|---|
| 待调研 | 还没查 | — |
| 有源码线索 | 上游或社区有代码，没编译过 | 链接 |
| 离线通过 | 编译、QEMU、单元测试、脚本自检通过。只说明代码逻辑符合设计，不说明硬件能用 | 命令、输入哈希、输出 |
| 真机启动 | 镜像在设备上跑起来了 | 镜像哈希、启动 ID、日志 |
| 真机通过 | 功能在真机上用真实结果验证过 | 真实结果 + 硬件指标 + 场景 + 证据位置 |
| 冷启动通过 | 冷启动和全新安装下也通过，不依赖之前留下的状态 | 冷启动日志 |
| 可发布 | 以上全部，而且是最终发布的那份文件 | 发布文件哈希 |

需要感官判断的项目（画面、声音、手感），人不在场时只能写"机器指标通过，待人眼确认"；有独立而充分的判据的项目（网络、编码结果的独立解码读回）不必等人。硬件判据和人工确认分开记录，不互相冒充。

## 这些都不算功能通过

驱动加载成功、sysfs 节点存在、服务 active、D-Bus 属性变化、声卡或 PCM 出现、远端处理器 running、`hci0 up`、`/dev/fb0` 能写、显存里有图像、vblank 和帧计数在增长、截图正常、Fastboot 返回 OKAY、QEMU 通过、程序注入的输入事件、单元测试通过、测试用的模拟数据和被测代码基于同一个错误假设而"互相吻合"。

计数、读回、进程在跑只证明它们自己。vblank、帧计数和截图只证明 SoC 一侧在出帧：背光关着、面板没跟上时它们照样正常。新的显示模式、面板时序和显示生命周期，要有面板侧证据（人眼、外部相机或面板读回）才算通过。

单元测试证明实现符合设计，不证明设计符合现实；一条断言如果在守护一个可疑的边界，修复时连断言一起审。

## 证据阶梯

先定这项决定需要什么证据，再取满足它的最便宜办法，依次考虑：

1. 离线推导：读源码、原厂配置、已有日志。
2. 软件判据：寄存器读回、计数器、日志里的具体行。
3. 无人值守运行：脚本驱动、自动判定、自动恢复。
4. 日常使用中的后台取证：长时间记录器在用户正常使用时采集。
5. 用户动作：只留物理上非人不可、而且会改变决定的。

较低层的证据不冒充功能或发布验收；但能用低层证据回答的问题，不要升级到用户动作。

## 各子系统的证据

| 子系统 | 硬件指标 | 真实结果 |
|---|---|---|
| 启动 | USB 约 1 秒内断开、时间标记、按时自动重启 | — |
| 显示 | 帧计数按刷新率增长、无欠载、拓扑与原厂一致或显存采样有多种颜色；面板读回（读回有效、覆盖目标现象） | 人眼看到正确画面（每个新模式至少一次） |
| 触控 | 固件状态、中断计数、输入事件 | 手指点击、滑动、多指、四角 |
| GPU | 渲染器是硬件 GPU、逐像素正确、无 GPU 挂起 | 复杂应用画面正确 |
| Wi-Fi | board 匹配日志、实际频点、DHCP、ping、吞吐 | — |
| 蓝牙 | 冷启动可用、地址正确、能扫描 | 配对设备实际工作 |
| 音频 | 播放指针推进、寄存器读回、调参文件版本、回环 | 人耳听到；麦克风外部声源加无声对照 |
| 充电 | 15 到 30 分钟电量和电压趋势、电流 | — |
| 旋转 | 原始数据、服务输出、合成器状态 | 实际摆放和截图 |
| 按键、锁屏 | 输入事件、显示电源状态、锁屏状态 | 人眼 |
| 休眠 | 成功计数、墙上时间实睡时长、启动 ID 不变、唤醒源；省电要看 SoC 是否进入最深状态（例如 CX 塌缩计数） | — |
| 调频与温控 | 硬件计数器的实际频率（有 AMU 时读 `cpuinfo_avg_freq`），不是 `scaling_cur_freq` 这类请求值 | 跑分与原厂对比 |

## 测试方法

- **冷启动和对照。** 改了服务、socket、udev、initramfs、启动参数，都要冷启动测试，并做对照（撤掉修改后问题重新出现，或关闭功能后确实不可用）。运行中切换开关不能代替冷启动。
- **全新安装。** 没有保存的 ALSA 状态，没有手动重启过的服务，没有上次启动留下的设置。
- **正对照。** 已知正确的输入在你的工具里也必须得到正确结果，否则先修工具。
- **调试代码也是变量。** 加了调试代码后问题消失，说明调试代码改变了行为；对照组也要加同样的代码。
- **测试数据用真机格式。** 至少保存一份真机原始输出（换行符、真实地址、真实时序）作为测试数据。
- **列出测试环境和真机的差异。** 逐条判断会不会让结论失真。最常见的盲区是测试通道本身：USB 调试线一直插着，"拔线、用电池"这个最常见的状态就从来没测过；要专门安排一次，并准备不依赖 USB 就能回来的办法。
- **诊断设置也是变量。** 为抓日志改的参数（例如 `console_suspend=N`）、观测本身（读 `clk_summary` 会唤醒所有提供者）、截图快门音（会拉起音频流）都会改变被测系统。决定性测量前恢复产品默认，结论里写明开着哪些诊断项。
- **把运行中的偶发问题变成确定复现。** 找一个能稳定触发同一机制的子问题（例如用 SIGKILL 热重启服务代替等待长时间闲置），或把竞态窗口人为放大（在可疑位置加延时），再做可证伪的实验；修复版在同样放大的条件下也要通过。
- **组合候选通过后拆开验证**，每个改动要有自己的收益证据，否则会带进只是"恰好够长的等待"一类的副作用。
- **安全问题立即停止，其他功能失败继续收集证据**，最后统一报告，避免一个失败浪费整个测试窗口。

## 测试范围

- 只测这次改动可能弄坏的和要达到的目标；时长和轮数由所需精度决定。长测试开工前逐项问"这一项会改变哪个决定"，答不出就删。
- 新功能的生命周期先用可替换的包或 RAM 启动验证，再组装正式发布物。
- 完整回归（含长时间等待的生命周期和预算项）每个版本只在最终候选上做一次，中间候选不跑全套。
- 发布验收固定包含用户最常碰的生命周期：熄屏和亮屏、锁屏、长时间熄屏后唤醒、登录界面唤醒，每项都用真实输入检查显示和触控；拔线、用电池挂起和唤醒。

## 测试自动化

目标：每次上机测试由脚本完成，用户只做必须由人完成的事。

**上机编排脚本**
- 一条命令完成：检查设备身份、电量、调试通道 → 启动候选镜像 → 等待 → 采集 → 判定 → 恢复到原系统。
- 每一步有超时；输出机器可读的结果（例如 JSON），包含版本信息、每项指标、通过或失败、证据路径。
- 某项功能失败时继续采集其他功能的证据；只有安全相关的失败才立即停止。
- 用户到场前先完整跑一遍主机侧检查（USB 接口、地址、Fastboot 身份、换行符、命令长度），主机脚本的问题不能浪费真机机会。

**设备侧自检**
- 每个功能写一个自检命令，输出结论和原始数据，开机后自动运行并把结果传回主机。
- 自检直接读硬件指标（计数器、寄存器、日志里的具体行），不只看服务状态。

**自动恢复**
- 每个上机镜像都带超时自动重启；回程机制随镜像本身生效（例如命令行带一个标记，已装系统里的单元见到标记就到点重启回已装内核；内建硬件看门狗并由 systemd 武装），不能依赖启动后再经 SSH 安装的定时器：SSH 不通时它根本不存在。
- 高风险操作前在设备上先设好回退定时器（例如切换 USB 角色前）；定时唤醒一律用相对时间（`+N` 秒），RTC 读数和系统时间可能不在同一个时间域。
- 守卫自己出错时不能取消回程：只有确认的用户会话或真实输入才能取消。
- 自动恢复本身要先在能确定回来的短窗口里验证过，才能用于无人值守测试。
- 主机看不到设备（USB 不再枚举、SSH 断开）不等于整机挂死，先找第二个独立信号（屏幕、触控、另一条通道），否则按"活着但连不上"处理，不要急着请用户长按电源键。

**用机器代替人的手段**

| 要确认的 | 自动化手段 | 仍需人确认的 |
|---|---|---|
| 画面 | 显示接口帧计数、欠载标志、CRC、显存采样、合成器截图并与预期像素对比 | 首次点亮、颜色和闪烁 |
| 触控和按键 | 用 uinput 注入事件验证软件链路；记录真实事件的坐标和时序 | 真实手指、真实按键（至少一次） |
| 声音 | 回环录音检测测试音频率、功放电气反馈、播放指针和错误计数 | 首次出声、音量是否合适 |
| 麦克风 | 设备自己播放测试音再录音；有声和无声两组对照 | — |
| 网络 | 自动连接测试热点、DHCP、ping、吞吐、重连 | — |
| 蓝牙 | 自动扫描；配对可用另一台主机脚本完成 | 耳机或键鼠实际可用（至少一次） |
| 应用 | 逐个启动常用应用，用 AT-SPI 找窗口、截图、检测崩溃和空白 | 最后整体看一遍 |
| 充电 | 定时记录电量、电压、电流，自动算趋势 | 插拔充电器的物理动作 |
| 旋转 | 自动记录原始数据和合成器状态 | 实际摆放四个方向 |
| 启动性能 | 多次冷启动，自动检查时间预算 | — |

注意：注入的事件和截图只证明软件链路，不能代替真实手指、真实画面的首次验收。

**桌面自动化的具体做法（GNOME）**：经调试通道操作。截图用桌面门户（xdg-desktop-portal）的 Screenshot 接口并预先授权，避免弹窗（门户每次截图还会在用户的图片目录留一份原件，测试后只删自己的）；点按、滑动、打字用 Mutter 的 RemoteDesktop 虚拟输入，不必走 uinput，也不用开第二个 Shell；坐标是逻辑像素，随缩放变化；锁屏时截图是全黑的，测试前先解锁（测试机可关自动锁屏，不进产品）；没有列窗口接口时用截图判断。帧率和渲染测试可以用无头 GNOME（`gnome-shell --headless --virtual-monitor`）。

**冷启动验收工具**
- 把冷启动判据做成一个脚本：启动时间各阶段、显示和 GPU 硬件指标、失败的服务、模块是否来自当前内核、内存带宽。每次内核或启动路径更新后跑一次。
- 采集要等系统完全起来（例如开机 45 秒以后），太早会把"仍在启动"误报为失败。

**回归**
- 按改动的影响范围选：改了启动路径就冷启动，改了某个子系统就测它和它的生命周期；最终候选上做一次完整回归（见上面的"测试范围"）。结果与上一版对比，退步立即标出。
- 内核换代另做缺行清单和新旧开机日志比对（见 `process.md` 的"内核换代"）。
- 主机侧单元测试和 QEMU 测试用来验证逻辑，测试数据来自真机原始输出。

**测试本身也要测**
- 给每个检查准备一个应该失败的输入，确认它真的会报失败。
- 空输出、超时、命令找不到都算失败。
- 测试用的模拟数据不能和被测代码基于同一个假设。
- 每个判据写明适用范围：静置时成立的阈值套到贴近热源的传感器、套到另一个负载形态上，会制造假失败。
- 把原始日志里的失败行当作发现来扫描（例如挂起被拒的 `device_prepare(): ... returns`、`Failed to put system to sleep`），做成跨启动的自动检查；问题常常在被正式发现之前就已经出现在日志里。

**用户参与**（原则见 `discipline.md` 第 7 节）
- 只保留人眼、人耳、手指、物理摆放、插拔。
- 把需要用户做的事合并成一份清单，提前告诉用户时间和要看的东西，每项给明确的观察点和回答方式（例如"是/否"）。
- 需要人眼判决时，把开关做成运行时参数，在同一次启动里做 A/B/A：用户只报看到的结果，切换由你远程执行；基线不复现就不判。
- 用户回答也记进实验记录，与机器指标分开写。
- 已经确认过的手势、按键不反复让用户做。

## 启动时间和性能预算

单次检查发现不了偶发的慢启动，要看多次冷启动。为每台设备定一组预算并在每次更新时检查，例如：

- 借用画面的显示驱动在启动后 1 秒内接管，相关时钟从 initramfs 起一直被占用。
- 切换到真正根文件系统、显示管理器启动、GPU 固件加载各有上限（例如 10 秒、20 秒、20 秒）。
- GPU 在启动后几分钟内没有错误。
- 一个简单的内存拷贝测试达到预期带宽（用于发现内存路径被降速）。
- 刷新率正常、桌面颜色正常。
- 普通重启、Linux 切到 Android、Android 切到 Linux 的耗时。

## 实验记录

每次实验前写四句话：
1. 只改了什么。
2. 如果结果是 A，排除了什么。
3. 如果结果是 B，排除了什么。
4. 用哪个机器指标判断通过。

判定"无效"之前，先说明其他条件为什么都是好的；说不清时写"在当前未知条件下没有看到改善"。

## 首版标准

别人能按文档构建、安装、使用。不要求所有外设完成，不要求全部提交上游。
