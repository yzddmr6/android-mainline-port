# 工作纪律

移植周期长、失败多、经常换人或换 agent 接手。能否持续推进，主要取决于三件事：记录是否及时准确，决定是否由该做决定的人做，用户的时间有没有被珍惜。某次调试多聪明反而是次要的。下面写的是必须做到的事和背后的原因；文档的具体格式由你自己决定，清楚、好找、能被下一个人直接接手即可。

## 1. 必须有的文档，以及要记什么

| 文档 | 要记什么 |
|---|---|
| `AGENTS.md`（或项目的 agent 规则文件） | 设备和目标；用户已确认的决策（带日期）；授权边界；设备安全规则；提交署名规则；什么不能进公开仓。所有执行者（不同的 AI 编程工具、子 agent）读同一份。不写进度，不写事件经过（事件写进复盘或历史档）。 |
| 状态页 | 一屏以内只写现在：每条版本线的状态、**唯一的下一步**、当前阻塞、等用户的事；功能表每项一句话（只用状态词）加详细文档链接。过时内容移出，历史交给 git。 |
| 交接页 | 此刻接手要知道的：谁在操作哪台设备、到什么时候，正在跑的任务和执行者，现场注意事项。过时即删。 |
| 工作日志 | 按日期记**结论的变化**，一两行加链接，不记流水账，不复制状态页段落。 |
| 每个功能一份详细文档 | 路线和复用来源；证据（每条带版本信息）；最早出错的层；被否定的假设（保留原文，追加适用范围）；完成标准；下一个实验。 |
| **技术债表（唯一一份）** | 见下一节。 |
| 放弃方案记录 | 放弃了什么、证据、在什么条件下成立、重新考虑需要什么新证据。 |
| 设备与工具的坑 | 每条"现象 → 做法"一两行，写设备任务时让执行者对照。修好的坑删掉或改写成仍然有效的部分。 |
| 复盘 | 有技术深度的问题解决后写一篇：结论、最初的错误判断、排查、根因、修法、可复用的方法。 |
| 实验记录 | 改了什么、预期结果各说明什么、判据、结果（机器证据和人工确认分开）、证据位置。 |
| 对外文档 | 写给第一次接触项目的人：风险、安装、升级、回到 Android、支持表。不写内部代号和进度细节。 |

状态词见 `verification.md`。

为什么要一个事实只写一处：同一结论写在状态页、交接页、日志和功能文档四处，迟早互相矛盾，接手的人分不清哪句是现在的。只增不删的状态页会长到没人读完，"唯一的下一步"也就失去了意义。

## 2. 技术债：快速方案必须登记

为了尽快点亮或跑通，可以先用临时做法（例如借用固件画面、固定发射功率、保守增益、调试参数、全局忽略开关、应用级绕过、手工步骤）。这完全可以，但**每一个临时做法都要登记在一份统一的技术债表里**，之后集中还。

每条至少写清：
- 做了什么临时处理，放在哪里（文件、包、配置项）。
- 为什么暂时需要它，正确的做法是什么。
- 它带来的影响和风险（功能、功耗、安全、维护）。
- 去掉它的条件（什么完成之后、怎么验证可以去掉）。
- 关联的功能文档。

规则：
- 加临时做法和登记技术债在同一个提交里完成。
- 功能"跑通"不等于债还清；链路通了之后仍要回来收敛。
- 诊断阶段为满足依赖顺手关掉的配置、加上的参数，也是临时做法：合并配置片段时逐项复核，否则会在产品里静默存在很久。
- 普通的"还没做的功能"不放技术债表，放状态页。
- 定期按影响排序过一遍，挑出下一批要还的。

## 3. 什么时候写

- 开始一个功能前：写目标、路线、完成标准。
- 每次上机前：写实验的预期和判据；上机后当天写结果和证据位置。
- 结论变化：更新工作日志和状态页。
- 加临时做法：登记技术债。
- 放弃方案：写放弃记录。
- 用户做了决定：写进 AGENTS.md，带日期，保留原话的实质。
- 同样的失败第二次出现：写一段分析，包括最早出错的层、已排除的假设、下一个能证伪的实验。
- 有技术深度的问题解决后：写复盘。
- **会话结束或交接前**：更新状态页的下一步和阻塞、交接页的设备状态。下一个接手的人或 agent 只看文档就能继续。
- 执行者完成任务时，也要按同样的要求更新它负责的记录；你来检查。

写法：
- 写结论和证据，不写流水账；原始日志放 `private/`，文档里只放路径。
- 失败和回退追加新记录，不改旧记录；推断被推翻时显式撤回，并写明修订边界。
- 每条真机结论带：源码提交、镜像哈希、测试场景、证据位置。
- 字节转储、寄存器读数要绑定来源（设备路径、节点、基址），否则同名的两个单元会被混为一谈。

## 4. 目录结构

推荐一个私有工作区，里面嵌套两个独立的公开仓库（工作区的 `.gitignore` 忽略它们）：

```
<项目>-workspace/                 私有工作区，仅本地 Git
├── AGENTS.md
├── docs/                         状态页、交接页、工作日志、技术债、放弃方案、功能文档、坑、复盘
├── tools/                        内部脚本：上机编排、采集、分析
├── sources/                      参考仓库（只读，记录来源和提交）
├── private/                      Git 忽略：原始日志、备份、本机唯一数据
├── out/                          Git 忽略：构建输出和缓存
├── kernel/                       内核仓（独立 Git，公开，保留上游历史）
└── public/<项目>/                集成仓（独立 Git，公开）
    ├── README.md                 风险、快速开始、"让 AI 帮你安装"提示词、支持表
    ├── docs/                     安装、升级、构建、开发文档
    ├── kernel/                   内核提交和配置的锁定信息、ABI 账本
    ├── device/                   设备用户态
    ├── packaging/                各个软件包
    ├── firmware/                 原厂固件（用户同意分发时）
    ├── tools/                    构建、打包、安装、切换、测试
    └── tests/                    测试，测试数据来自真机
```

- 同一份代码只放一个地方：内核改动在内核仓，集成代码在集成仓，私有工作区只放记录和内部脚本。不保存长期同步的副本。
- 序列号、MAC、蓝牙地址、校准数据、备份，以及包含这些信息的日志，只放隔离的本地资料目录，私有仓也不提交。密码只经受限管道传递，不写进持久文件、命令行和日志。
- 设备凭据若暂存在受限的 tmpfs 中，要把主机重启、注销或运行时目录清理视为凭据失效。进入依赖凭据的操作前检查存在性、属主和权限，不输出内容；缺失时从已授权的凭据入口安全重新注入，再验证访问。恢复步骤写进本地运维说明，未恢复前不启动依赖它的无人值守操作；不能为跨重启省事把明文复制到持久文件、命令行、日志或提交。
- 修复必须进入可导出的补丁序列（内核仓的提交），不能只存在某个临时工作目录；重建分支时最容易丢的就是这类提交。
- 多台设备的项目各有自己的工作区；两边共同的工作方式可以逐字共用一节，用脚本比对，防止一边学到的教训另一边没有。

## 5. 提交与署名

- 第一天和用户定好：提交作者、仓库账号、仓库名、许可证。发布后再改已有提交的作者就要重写历史。
- AI 完成的提交如实写明实际使用的工具和模型（例如 `Co-Authored-By: <实际的模型名>`），换了工具或模型就写换后的，不固定写某一个；不伪造人类署名，不代人加 `Signed-off-by` 或 `Tested-by`。向上游投稿时按当时上游文档的格式另加，格式会变。
- 引入第三方提交保留原作者、日期和原有尾注，不加 AI 尾注；本地修改另成提交；记录来源仓库和提交。
- 推送、建仓、发版、改可见性、重写历史，没有被已有授权覆盖的，都先问用户。

## 6. 决策与沟通

- **自己定的**：可逆、在已定范围内的实现选择，定了就做，不来回请示。
- **先问用户的**：不可逆或改写已发布历史；对外可见（推送、发布、公开文字、对外回复）；改变版本范围；占用用户的时间；超出已授权的范围或预算。给出选项、各自的代价和你的建议，写上最便宜的那个选项，由用户选。
- 大体量的上传、下载和长任务，先量一下（例如 `git rev-list --objects --disk-usage <远端分支>..HEAD` 估算待推送对象、`du`），只做目标需要的部分。
- 用户让你"评估""讨论"一个方案：做完必要的调查，给出利弊、判断和建议，等用户选，不宣布决定、不开工；同一消息里或此前已授权的其他工作照常推进。用户授权"自己做完、不要提问"时，范围内不再问。
- 汇报先说结论：改了什么、还差什么、下一步、需要用户做什么；细节等用户问了再给。
- 用户的授权口径会随情境变化。授权只覆盖它说到的范围，写进 AGENTS.md 时带日期和范围。

## 7. 用户的时间

用户的时间是整个项目里最贵的资源。代价最高的一类失误，是用户到场后才发现脚本没空跑、前提没查、指令来回改、回归没先做。每次只补一条针对症状的规则挡不住它，共同的根因只有一个：交给用户的每一步，都没有先由你在真机上按同一顺序跑过。

- **用户不是测试员**：交给用户之前，你已经在真机上无人值守跑过接近日常用法的负载。
- **证据阶梯**：先定这项决定需要什么证据，再依次考虑最便宜的办法：离线推导（读源码、原厂配置）→ 软件判据 → 无人值守运行 → 日常使用中的后台取证 → 用户动作。低层证据不冒充功能或发布验收。
- **只留非人不可的动作**：看、听、按、插拔、摆放，而且会改变发布决定的。逐项问：能不能改成软件判据？能不能等用户日常使用时后台记录？能不能合并？
- **空跑**：请用户动手前，在真机上空跑能自动执行的部分（编排、守卫、取证、恢复）；能读到的前提（电量、温度、会话、通道、所处区间）由脚本读，人工只补读不到的事实（例如手边有几个充电器、什么线缆）。
- **一次讲清**：开测前约好时间，一次问清会改变顺序的事实，再给一条不带条件分支、写明每步起止时刻的顺序；用户的动作尽量由设备上的通知逐步引导、按真实事件推进，等待上限放宽。确认可行后才说"开始"，说了不收回；出现安全问题（温度、供电、设备异常）照样立即中止并恢复。
- **谁来驱动**：用户在场的测试由正在和用户对话的那个会话亲自设计、驱动、判读，不经其他会话转发；开测前从其他会话收回设备驱动权。
- **离开即准备时间**：用户不在时把候选、脚本、清单都准备好，而不是在用户回来后才开始。
- 用户远程使用你的工具时，不要让他到主机或终端上操作；可恢复的桌面状态不要触发重启。

## 8. 工作量估算

不要按人日估。按下面的方法估一个区间：

1. 对每个子系统，列出还不确定的层：供电时钟、总线协议、内核驱动、远端处理器固件和协议、用户态、输出。硬件、固件和配置都等价、差异已核对、并在同 SoC 真机验证过的层不算；别人"声称支持"不算验证。
2. 每个不确定的层按几轮真机测试估：闭源协议、远端处理器、显示链路按上限；有厂商源码可读、有能工作的参照实现按下限。
3. 按执行者的实际耗时分开估：主动处理、构建与打包、真机验证、外部等待（用户、上游、充电）。未知的硬件故障只估下一次决定需要的窗口。
4. 加上几乎必然出现的成本：主机端脚本的问题、设备不在手边的时间、重复踩已知的坑（先读 `experience/` 可以大部分避免）。
5. 输出：时间区间、最大的三个不确定因素、什么条件下区间会缩小。报给用户的是预计时间，不是预算上限。

真正的瓶颈通常是可用的真机测试次数，不是代码量。显示、音频、Wi-Fi、休眠往往最耗时。效率最高的情况是"设备在线、候选已准备好、授权明确"，要为这种时段做准备，而不是在设备不在时堆积未测试的候选。

## 9. 委派

- **按活的轻重选执行者**：小而直接的检查和改动自己做，省掉来回切换上下文；重活、脏活、耗时长或会分散注意力的才委派，比如构建、打包、成批离线实验、大范围阅读。只读任务用只读沙箱。
- **任务书以"要回答的决定"为中心**：写这次结果用来决定什么、需要哪类证据（严格程度与风险相称：发布门槛严，探索到能区分假设为止）、硬约束（设备安全、必须照做的安全操作顺序、接口约定、提交边界、不得碰的目录）和预算，调查方法交给执行者。不列与结论无关的步骤、测试项数量和轮次：写了清单，执行者就会照单做满，额度和时间都花在不改变结论的事上。相关的几个假设合成一个带决策树的任务，同一版本的改动合成一个候选，一次上机做完。
- **预算按决定累计**：同一个决定的续任务不重新拿预算，续任务要说清新增的信息会改变什么。长任务开工前逐项问"这一项会改变哪个决定"，答不出就删。
- **不外包思考**：执行者交工具、数据和结论草稿；问题定义、根因判断、测试方案和给用户的话由你自己做、自己写，不原样转述执行者的产出。执行者的关键结论（尤其"原厂做了/没做 X""上游没有 Y"）打开源码或原始数据核一次再用。
- **执行者看不到你的记忆**：它只读规则文件和任务书。设备安全约束和已知的坑要写进所有执行者都会读的仓库文档，设备任务书引用它；只写在某个 agent 私有记忆里的经验，等于执行者不知道。
- **监督靠事前设计和事件**：完成通知到了就认真验收；等待设一个超时，到点看一次是否在打转、路线是否还对，没有决定性进展就止损重定，其余时间不轮询。执行者报"通过"不免检：看它的测试方式是否与真实使用一致（冷启动还是运行中切换、真机还是模拟器）。
- **等待设备或长任务**：优先用完成事件；否则一次执行带总超时的阻塞命令，把必要的探测留在命令内部，按事件时间尺度设置间隔，普通长任务等待不短于一分钟。只在完成、超时或异常时返回，不在模型层反复读状态、开新命令等待或输出无变化进度。需要短时间硬件采样时由采集程序完成，不把采样频率变成模型调用频率。
- **后台进程**：执行者启动、要活过它这一轮的主机进程（监视器、记录器），交给生命周期明确的进程管理器（例如 `systemd-run --user`，用户服务要开 linger），并验证会话结束后它还活着；`setsid` 只脱离进程组和会话，逃不出按 cgroup 的清理。等周期采样的日志时同时看修改时间是否还在前进：只认关键字分不清"还没到"和"写的人已经没了"；更可靠的是进程管理器的状态或独立心跳。
- 执行者默认不碰设备；两个执行者不共享源码目录、输出目录或设备。高风险的上机方案，先让一个独立的执行者专门挑错，常能在上机前发现严重问题。

## 10. 改规则本身

规则文件会越改越长、越改越个案化。改的时候：

- 进规则的条件：通用（不止适用于那一次）、持久（下个月仍对）、改变做法（没有它接手者会做错）。三条缺一不进；个案、一次性授权、事件经过放复盘或历史档。
- 写原则和判断方法，不写那一次的症状，不写没人定过的死数字。
- 精简或重组时逐条对照旧文本，确认没有丢掉原有决定和限定语（例如"硬件判据与目视分开记录、不互相冒充"被精简成"人不在场时用硬件判据代替目视"，之后就出现了 vblank 正常而面板黑屏的误判）。
- 命令写成能照字面执行的形式；给人看的简写会被执行者照字面跑错。
- 定稿前让一个只拿到原始材料、没看过你方案的审查者过一遍。
