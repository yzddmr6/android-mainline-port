# 关键技术决策与最佳实践

每个决策点写：**默认做法**；一组**规则**（遇到什么条件、该怎么做）；**为什么**（背后的机制，用来判断规则在新设备上是否还成立）；**不适用**（规则失效的情况）；需要时写**验收**。

这些规则是从多个项目的实际选择和结果里抽象出来的。条件不同时，按第 1 节的标准重新判断，并把理由记下来。

## 目录

1. 通用判断标准：怎么比较两条路线、标准接口优先、先查已有实现

4. 显示与输入：显示路线、默认刷新率、熄屏方案、外设和面板的电源生命周期、触控算法、键盘驱动形态
5. 电源：休眠方式、电源键与合盖、充电、系统时间、调频与温控、看门狗
6. 无线：Wi-Fi 监管域、功率与固件、蓝牙地址
7. 远端处理器外设：传感器路线、相机、视频硬解、扬声器增益

## 1. 通用判断标准

做任何选择时按这些问题逐个过一遍：

1. **离上游有多近？** 上游已合入 > 在审补丁 > 同 SoC 社区 > 自己已有的成果 > 自己写。本地补丁要写明上游合入后怎么删。
2. **出问题能不能退回去？** 优先选不改 bootloader 状态、不碰原厂关键分区、失败能自动恢复的方案。
3. **有没有真机证据？** 同类硬件上真正跑通的，优于"声称支持"的；别人的结论在本机验证前只算线索。
4. **谁来维护？** 上游或发行版维护的优于自己维护的。
5. **能不能替换？** 硬件层不绑定发行版、桌面、显示管理器或固定账户。
6. **是不是最小方案？** 不引入通用框架、常驻"管家"服务、重复的资源管理。
7. **用户要付出什么？** 性能、功耗、安全默认值、安装步骤、数据风险。
8. **来源和许可写清楚了吗？** 保留作者、来源提交和版权声明。项目怎样对待第三方许可，由用户定一次政策写进 AGENTS.md，不要每次复用都重新讨论。
9. **临时方案有没有退出条件？** 可以先用临时方案出结果，但同时开始长期方案，并登记技术债。

每个重要选择记一条：选项、代价、选择、理由、什么情况下重新评估。

### 比较两条实现路线
- **默认做法**：按这个顺序比：满足硬件协议和用户体验 → 不用的时候能停下来（省电、能挂起）→ 标准接口和上游可接受性 → 维护成本。
- **规则**：
  - 有人说"组件更少""全放在内核里""版本更新" → 这些都不能单独证明更好，回到上面的顺序逐项比。
  - 复杂算法和本机标定（例如原始数据型触控的手指识别）→ 放用户态更容易迭代、崩溃隔离好；内核只做传输、固件和生命周期，并把原始数据接口做稳定。
  - 厂商私有握手（例如快充认证）→ 放在可以独立更新的用户态是合理边界；电源限值、温控和生命周期留在内核或固件。
  - 传感器、相机这类有标准子系统的 → 长期向标准接口（IIO、完整的 libcamera 管线）靠拢；已经工作的专用链路不为形式统一推倒重写。
  - 参照项目的命名可能和你相反（例如两家把同一对面板的厂商名写反）→ 按原厂标识核对，不按名字。
- **为什么**：截图里看不出差别的两种实现，差别在升级、待机和几年后的维护上。

### 标准接口优先
- **默认做法**：硬件通过标准接口报告事实，系统已有的策略组件决定行为。合盖用 `gpio-keys` 上报 `SW_LID`，交给 logind；电池走 power_supply；按键走 input；显示走 DRM/KMS。
- **规则**：
  - 想写一个守护进程读传感器、判断状态、再去调背光和输入（例如用磁力计判断合盖）→ 先找有没有更直接的硬件信号（霍尔开关）和对应的标准事件；守护进程要自己处理阈值、滞回、防误触、和其他关屏来源的协调，这些都会变成长期维护。
  - 标准事件接上之后 → 真正的工作量在睡眠和唤醒：接线、极性、唤醒条件，以及系统睡着以后这根信号是否还可靠。
- **为什么**：驱动只说"发生了什么"，策略层说"怎么办"；以后调整策略、换发行版，都不用重新判断硬件。

### 先查已有实现
- **默认做法**：决定自己写之前、每个版本定范围之前，各做一次社区复查。
- **规则**：
  - 按接口找，不按名字找：用每个实现都绕不开的词搜（芯片名或代号、驱动名、`/dev` 节点、协议名、固件文件名），GitHub 之外也查 Codeberg、GitLab 和邮件列表。
  - 列出已经在跟踪的作者的全部仓库，按推送时间排序；查你导入来源的 fork 网络。
  - 记下复查日期，以及每项发现改变了哪个决定。
  - 别人的代码可能也是 AI 写的、互相抄的 → 按测试判断质量，不按名气。
- **为什么**：按已知项目名找，会漏掉同一作者后来的新仓库、换了名字的 fork 和别的平台上的实现；复查放在设计之后，就只能用来补救。

## 2. 准备与启动

### 备份与 root
- **默认做法**：先取得 root（按设备的启动布局和 root 工具的安装模式修改对应的镜像，GKI 设备常见是 init_boot，也可能是 boot；先保存同版本的原厂镜像），按用户确认的范围逐分区备份（通常排除 userdata 和 super，写明没备份的部分靠什么恢复），另存每个 LUN 的主备 GPT，主机和设备两侧哈希一致。
- **规则**：
  - 想在原厂内核上拼一个最小 RAM 探针来读分区 → 不要做，直接 root 原厂系统更快。
  - 不能或不想 root Android → 临时 `fastboot boot` 一个带 root 的 recovery，把块设备设为只读后再读取。
  - 有可以再次下载并校验的官方 OTA → 可以用它作为系统分区的恢复源、减少备份量；但 persist、校准等本机数据必须单独备份。
  - 双系统需要 Android 侧能写启动分区 → 选不动 Linux 要轮换的那几个启动分区的 root 方式（例如只改 init_boot），Android 更新后重新打补丁。
- **为什么**：持久写入前必须有退路；原厂内核的 USB 往往依赖显示、相机等时钟控制器先就绪，最小探针拿不到 USB，也得不到新信息。
- **不适用**：厂商提供能无损还原全部分区（包括校准）的救援工具时，备份范围可以缩小，本机数据仍要备份。

### 设备树路线
- **默认做法**：上游 SoC dtsi + 自写板级文件。每个数值来自本机原厂证据；固件留下仍在使用的资源，写进真正的消费者节点。
- **规则**：
  - 目标只是快速演示 → 可以用原厂设备树 + overlay + `clk_ignore_unused pd_ignore_unused iommu.passthrough=1`，但要告诉用户这条路做不了休眠、省电和上游化。
  - 怀疑是资源回收引起的故障 → 分开试：`clk_ignore_unused` 对应时钟回收，`pd_ignore_unused` 对应电源域回收；`iommu.passthrough=1` 改的是 DMA 地址转换，是另一个假设。某个参数让现象消失，只说明嫌疑在对应那一类；找到具体消费者后撤掉参数，把资源需求写进消费者。
  - 某个调试参数删掉就黑屏（"承重参数"）→ 不要带进产品；在资源回收前后各导出一次时钟和电源域状态，二分出具体是哪个资源。
  - 同机型的社区项目走的是原厂设备树路线 → 借用它的驱动和用户态，不借全局保活参数。
- **为什么**：全局保活让内核永远不能关闭固件留下的资源，也没有 IOMMU 隔离；原厂设备树按下游驱动写，原厂系统更新后 overlay 可能失配。正确的资源声明只需做一次，之后休眠、省电、上游化都建立在它上面。
- **不适用**：一次性演示或实验设备。
- **验收**：没有全局绕过参数；没有长期挂起的 sync_state；完整模块集多次冷启动稳定。

### 内建还是模块
- **默认做法**：启动、恢复、调试通道需要的驱动，借用固件画面所依赖的资源提供者，显示组件依赖链上的驱动，电源键，编进内核或完整放进 initramfs；其他按上游默认做模块，发布完整模块目录。
- **规则**：
  - 早期镜像里还没有模块目录 → 启动和恢复依赖全部 `=y`，并尽早建立"版本化完整模块目录"的交付方式。
  - 走借用固件画面的路线 → 显示时钟控制器等资源提供者必须内建，并在 `late_initcall` 之前绑定。
  - 第一次测试的新驱动（尤其时钟控制器、多媒体）→ 编成模块，调试通道建立后手动加载；不要一次把多个新驱动编进内核。
  - 驱动处在某个组件框架的依赖链上（例如 Type-C 切换芯片之于显示）→ 保证它在最早使用者之前绑定，通常就是内建或放进 initramfs，否则整条链等待。
  - 要裁剪模块数量 → 按依赖闭包裁，不按 `lsmod` 的结果裁；裁剪后用完整场景回归。
  - 功能静默缺失 → 先看最终 `.config`、模块目录是否交付、`devices_deferred`，再怀疑设备树；注意 `A depends on B || !B` 会把 A 也压成模块。
- **为什么**：没有模块目录时 `=m` 等于不存在且不报错；模块绑定晚于资源回收点时，资源已经被关掉；没人跑过的驱动可能在早期挂死总线，做成模块就能在调试通道建立之后再加载、挂死前拿到日志（模块仍在内核里运行，照样可能挂死整机，所以仍要有独立的回程）。
- **不适用**：发行版通用内核已经覆盖该设备时，按发行版的模块策略即可。

### initramfs
- **默认做法**：首次启动和 RAM 阶段用自写的最小 BusyBox initramfs；产品阶段用发行版生成器（Ubuntu 是 dracut），`hostonly="no"`，设备早期逻辑做成生成器的模块。
- **规则**：
  - 早期逻辑很重（自定义恢复、复杂切根）→ 可以一直用自写 initramfs，接受自己维护。
  - 自写 initramfs 要校验根文件系统 → 只校验项目自己的文件，并提供改动后重新封装的流程；否则发行版更新或设备上的热修会让启动被拒。
  - 发行版生成器在构建机上很慢 → 改为在设备上生成。
  - initramfs 体积接近启动分区余量 → 核对模块和固件清单，不要靠提高压缩等级（有的打包器会忽略这个参数）。
  - 包配置停在 half-configured → 先查发行版的启动部署工具（Debian 系是 flash-kernel）和项目钩子。
- **为什么**：发行版生成器跟随系统更新，长期维护成本低；自写的版本早期最可控。
- **不适用**：发行版本身已支持该设备的启动方式时，直接用发行版的完整流程。

### 启动镜像格式
- **默认做法**：RAM 测试用 header v2（kernel + ramdisk + DTB）；持久启动按原厂结构生成（GKI 设备通常是 boot/init_boot/vendor_boot 三件套）并自签 AVB 尾部；打包时检查设备树身份（msm-id/board-id）、命令行长度和镜像大小。
- **规则**：
  - 新设备 → 用时标探针分别实测 `fastboot boot` 和冷启动接受的格式；同 SoC 其他设备的结论只作参考。
  - `fastboot boot` 返回 OKAY 但停在 Fastboot、pstore 为空 → 先对比设备树身份和历史上能启动的版本。
  - 冷启动直接进 Fastboot → 先查 vbmeta 链要求的 AVB 尾部。
  - 较早一代的 bootloader 只认单个 boot 镜像 → 双系统只轮换 boot 分区。
- **为什么**：bootloader 在跳到内核之前按设备树身份选择和校验，失败时内核侧没有任何证据；不同代的 ABL 对 ramdisk 的交付方式不同。
- **不适用**：使用 U-Boot、LK 等其他引导程序的平台，按其规则自证。

### 早期日志
- **默认做法**：原厂设备树里有固件保留的固定内存就用 pstore/ramoops；没有就用 netconsole（网络起来之后才有）；屏幕 earlycon 作补充。写明每条通道最早从哪个阶段开始可用。
- **规则**：
  - 保留区是动态分配的 → 不要猜地址，改用 netconsole。
  - 内核在交接后静默挂死 → 想办法把崩溃打到屏幕上（例如借用固件画面的 earlycon），常能直接定位。
  - pstore 内容跨重启出现损坏 → 不把它当唯一证据，配合实时通道。
- **为什么**：ramoops 写到不安全的地址会破坏数据或被固件覆盖。

### 调试通道
- **默认做法**：RAM 阶段用 USB NCM + telnet/SSH + 超时回退；产品阶段用 socket 激活的 SSH，绑定固定的 USB 网段地址并 `FreeBind=yes`，用 `IPAddressAllow`/`IPAddressDeny` 只接受 USB 网段；默认关闭、可显式打开、重启保持。
- **规则**：
  - 想让 SSH 只接受 USB 网卡 → 不用 `BindToDevice`（开机时网卡还不存在，会造成启动依赖死锁）；`IPAddressAllow` 只限制来源网段，要严格限定入接口，再加一条按入接口过滤的防火墙规则（例如 nftables 的 `iifname`）。
  - 改了调试包或通道相关的服务 → 冷启动验证，并验证"从旧版升级"这条路径（升级时启用链接可能不会被重建）。
  - 第一次刷入测试机 → 先打开通道，确认有退路。
  - 只有一个 Type-C 口，要测 USB 主机模式 → 先建立并验证 Wi-Fi SSH 备用通道。
  - 主机侧没有串口权限 → 不用 USB 串口（ACM）作主通道。
- **为什么**：调试通道是无人值守工作的唯一前提；socket 绑定一个开机时还不存在的网卡会形成启动依赖死锁；正式镜像没有通道时，任何问题都只能等用户按键。
- **验收**：打开、关闭两种状态都冷启动验证，关闭时确实不可达。

### 候选内核的测试方式
- **默认做法**：先 RAM 启动验证，通过后才走正式升级路径持久安装。
- **规则**：
  - 在已安装的系统上测候选内核 → 设备上解包模块并 `depmod`、设备上生成 initramfs（不写槽），打 v2 RAM 镜像，命令行加 `softlockup_panic=1 hung_task_panic=1 oops=panic` 和 `panic=N`；离线确认候选的最终配置里有对应的检测器（`CONFIG_DETECT_HUNG_TASK`、`CONFIG_SOFTLOCKUP_DETECTOR`），启动后再确认 `/proc/sys/kernel/hung_task_panic` 存在；这些参数只处理被检测到的挂死，硬挂靠硬件看门狗；回程机制随镜像生效（见 `verification.md` 的自动恢复）；测完删除暂存文件。
  - 想直接装候选内核包 → 不要，包的钩子会写活动槽，候选有问题时设备会反复重启；重装同一版本的重建包时，也不要让它轮换掉回退槽。
  - 想在运行中替换某个硬件驱动模块 → 无人值守时不要卸载或重绑真实硬件驱动；在重启前暂存新模块，用新的 RAM 启动验证。
  - 第一个硬件故障出现（GPU 挂死、驱动报错风暴）→ 停测、取证、强制重启并汇报，同一次启动里不再继续测试。
  - 要强制重启 → 不先跑普通 `sync`（I/O 卡住时它自己就会阻塞）；向 `/proc/sysrq-trigger` 依次写 `s`、`u`、`b`，每次只写一个字符（它只认首字符，`echo s/u/b` 只会执行 `s`）；`s`、`u` 是异步的，各等日志出现 `Emergency Sync complete`、`Emergency Remount complete` 或到超时再写下一个。
  - 判断"挂死"→ 同一等待点持续几十秒没有进展，或内核报 hung task，才算；连续出图时显示提交线程短暂处于 D 状态是正常的。
- **为什么**：驱动卸载路径可能死锁；关机卡住时调试通道早已断开，设备只能等人按键。这些规则只写在经验库里不够，要写进每一份涉及设备的任务说明，或者执行者都会读的仓库文档。

## 3. 安装与双系统

### 双系统方案
- **默认做法**：活动槽镜像集轮换。两个系统都从活动槽启动；切换时整分区写入目标系统的镜像集并读回；不改槽属性、不碰另一个槽和 vbmeta；系统内用 `dd`；开机用 bootloader 支持的接口标记槽成功；Android 侧用 root 模块（例如 KernelSU 模块）切换；保留上一版 Linux 镜像集作回滚，并在主机上也存一份可用的镜像集。
- **前提**：几个启动分区的写入不是原子的，写到一半中断时要有不依赖这两个系统的回程（进 Fastboot 用主机上的镜像集刷回）；这条回程先验证过。
- **规则**：
  - 想把 Linux 放进 B 槽 → 先对比两槽各分区的哈希；B 槽常是旧固件链或空的；即使可用，也不要手写槽属性。
  - 想把 Linux 放进 recovery 分区 → 先确认 bootloader 是否只把它当 ramdisk（常见如此）。
  - 两个槽都起不来 → 先读 bootloader 记录的失败原因、`getvar all` 和 GUID 信息；不要用 `--set-active` 试；在已确认是槽元数据被改坏的这类 ABL 上，按备份的 GPT 恢复（先确认备份与当前布局匹配），再让 bootloader 自己重建槽状态。
  - 先做单系统 → 可以（B 槽保持原厂作退路），但双系统方案要尽早定，避免之后迁移。
  - 主机 `fastboot flash` 写过启动分区 → 重试计数可能被重置，需要开机标记成功的服务。
  - 用户想要开机菜单 → UEFI 或 U-Boot 作为后续方向，见第 9 节。
  - 想给用户一个"Linux 桌面坏了时回 Android"的紧急入口（例如开机按住某个键）→ 在 Linux 侧复用系统内切换工具，干净卸载文件系统后再重启；不要 `reboot -f` 硬切（ext4 留脏，Android 侧切换模块可能因此拒绝切回）。这个入口只覆盖 Linux 已经运行到那一步的故障，更早的故障仍靠 Fastboot 刷回。
- **为什么**：A/B 槽状态由 bootloader 私有逻辑维护，可能包括各分区类型 GUID 的互换和启动 LUN，只改属性位会被它的校验拒绝。
- **验收**：Linux → Android → Linux 真机各一次，加冷启动；槽属性前后对比；Android 依赖的固件分区完好。

### 分区容量
- **默认做法**：从 userdata 的位置划出空间给 Linux：缩小 userdata 就等于清除它（Android 的数据分区是加密的，不能安全地原地缩容），先取得用户清除数据的同意并备份，重建较小的 userdata 后由 Android 首启重新初始化；不要只改 GPT 里的边界。Linux 根 60 GiB（系统实际占用约 8–15 GB）；home 放在最后，后面有空闲空间时便于扩容；给用户 2–4 个具体方案选。
- **规则**：
  - 用户以后可能重装 Linux 但想保留数据 → 根和 home 分开。
  - super 是动态分区、Android 的加密数据 Linux 读不了 → 不要从这两处取空间。

### 根文件系统来源与交付
- **默认做法**：来源用发行版官方 ARM64 镜像的 squashfs 层，地址和哈希固定，设备部分做成软件包；交付用设备上 `mkfs.ext4` + 解压 tar，空分区在设备上格式化。
- **规则**：
  - 手工拼装根文件系统 → 改为官方层 + 软件包，否则容易漏固件目录、配置文件。
  - 必须发镜像 → 只编码已用块，刷写前汇总 RAW/FILL/DONT_CARE 的展开字节。
  - 目标分区上有旧数据 → 不要用按"内容为零"跳过块的 sparse 镜像（会把新文件系统必须清零的 inode 表、日志区一起跳过，旧日志可能被重放）；按新文件系统的位图只跳过空闲块可以，或者在设备上重新格式化。
  - 想在旧根上逐版叠加 → 不要，无法重建。
- **为什么**：sparse 的写零块由 bootloader 在后台慢速写入，几百 GiB 要几小时，期间 Fastboot 不响应；跳过块不清除旧内容。

### 安装器
- **默认做法**：首版就提供带安全门的安装方式，至少有一个维护镜像（只在内存里运行、带分区工具和 root shell、无会话超时回 Fastboot）。步骤：身份核对 → 电量 → 备份 → 布局确认 → 写入并读回 → 格式化与解压 → 首启前预置本机数据 → 写启动镜像并读回。
- **规则**：
  - 首启需要本机数据才能用的功能（触控标定、蓝牙地址）→ 首启前用维护镜像预置。
  - 有"保留数据"类选项 → 端到端测试设备侧确实没有格式化。
  - 双系统安装 → 校验 Android 依赖的全部固件分区，不只校验启动链。
  - 安装环境里的工具 → 先在真机内存环境里用小样本试；同一工具第二次出问题就换工具。
- **为什么**：手动 Fastboot 步骤一旦敲错分区名，没有任何保护；用户没有你的内部脚本。

## 4. 显示与输入

### 显示路线
- **默认做法**：上游显示驱动支持该 SoC、面板驱动可得时直接原生接管；否则先借用固件画面（simpledrm），并**同时**开始原生接管。
- **规则**：
  - 借用固件画面之后 → 不在它上面做亮度、熄屏、刷新率、休眠这些产品修补，这些全部依赖原生接管。
  - 要自写面板驱动 → 先把厂商显示驱动源码和原厂 debugfs 快照逐项对完，再做黑盒调参。
  - 社区已有原生实现 → 整组导入，面板命令与本机原厂逐条核对，板级数值取本机。
  - 原生接管的顺序 → 黄金快照 → 面板驱动 → 显示驱动做模块手动加载 →（固件画面在 SMMU 接管时开始缺页的 SoC 上）显示子系统加入 SMMU identity 列表 → 固件当前刷新率下接管 → 熄屏亮屏 → 其他刷新率（每档同时测触控）→ 夜灯等附加功能。
  - 零报错但花屏 → 先看管线拓扑和 DSC 参数，不要做多轮单变量调参。
- **为什么**：simpledrm 只拥有一块内存，不管硬件，GNOME 对它不提供内屏功能；借用画面还要专门防止资源回收。原生接管的成本主要在一次性的参数核对上，有厂商源码时可以大幅缩短。
- **验收**：人眼 + 硬件指标（帧计数、欠载、CRC），两者分开记录；每个新显示模式至少目视一次（vblank 正常而面板黑屏是真实发生过的）；几十次 DPMS 循环；多次冷启动满足时间预算。
- **对照原厂**：先把原厂显示控制器、PHY 的寄存器块整块导出，和本机逐项对比，再决定改哪几处；同时对照原厂的**顺序**（控制器软复位这类事件在寄存器快照里看不到）。原厂"每次配置做一次"的动作搬进主线前，先问它在主线框架里会被调用几次：时钟框架的 prepare 可能一次使能被调用多次。

### 默认刷新率
- **默认做法**：接管时先用固件当前的刷新率；原生稳定后再开放其他档位。
- **规则**：
  - 开放新档位 → 每档同时验证触控和 DPMS。
  - 某档被模式校验拒绝（显示核心时钟略超上限）→ 先确认 DSC 压缩后的真实需求；不要把时钟抬到 OPP 表之外。
  - 有手写笔 → 评估笔对刷新率的要求再定默认值。
- **为什么**：少一个变量，接管失败时更容易归因；触控固件的扫描节奏和显示刷新率有关。

### 熄屏方案
- **默认做法**：原生显示驱动的真正 DPMS 熄屏。
- **规则**：原生接管完成前 → 只关背光可以作为过渡，但要登记技术债，并注意它往往要适配特定桌面版本、功耗也高。
- **为什么**：只关背光时显示管线仍在运行。

### 外设和面板的电源生命周期（触控、键盘、配件）
- **默认做法**：跟随标准回调（`drm_panel_follower`、系统 PM 的 prepare/complete、suspend/resume），按原厂驱动的顺序写电源状态。回调里不等待"要等本回调返回之后才会发生"的事件（例如在面板 enable 回调里等触控首帧，而首帧要等显示 kickoff），这类等待排一个异步工作项并保留时间预算；断电前必须完成的停流和交接，在回调里有界地同步完成。异步工作项要持有所需的供电引用，并在熄屏、卸载、重新下载固件时取消或收敛。
- **规则**：
  - 熄屏后外设失效 → 检查面板复位后是否重新下载了外设固件。
  - 亮屏变慢、切换刷新率后外设失效 → 检查面板回调里是否在同步等待。
  - 休眠后外设失效 → 对照原厂驱动的熄屏、亮屏、休眠序列，找漏掉的一步。
  - 开机时已连接的配件不识别 → 分别采"开机时已连接"和"开机后再连接"两种场景的证据，找最早失败层。
  - 参考实现用了周期保活、自动复位、丢弃首个中断 → 不照搬，先查原厂的生命周期。
  - 想用服务自动重启来恢复 → 只能作为临时覆盖并登记技术债，不能当修复；每次重试都在重复同一个时序。
  - 判断外设固件"可以接受命令"→ 用固件自己的状态寄存器（例如复位状态到达正常运行态），不要拿"收到了第一帧数据"代替。
  - 和显示共用一颗芯片的外设（TDDI）出现整帧闪烁 → 查宿主读帧的 DMA 是否在途中撞上系统最深低功耗状态（见 `../experience/display.md`）。
- **为什么**：TDDI 面板复位会让触控固件丢失；回调里的同步等待会阻塞显示提交；保活和自动复位掩盖了生命周期错误；"有数据"只说明传输通了，不说明固件的状态机走到了能处理命令的那一步。
- **验收**：冷启动、熄屏再亮屏、休眠唤醒、拔插各场景分别用真实输入验证；每个刷新率都测。

### 触控算法（原始数据型 THP）
- **默认做法**：复用开源的用户态算法实现，内核只写传输层（固件下载、数据帧），本机标定从原厂提取且不进公开仓。
- **规则**：想在 Linux 上直接跑 Android 的触控 HAL → 不要，需要 Bionic 和 Binder 兼容层，维护成本高；从零自研算法同样不划算。

### 键盘配件的驱动形态
- **默认做法**：从厂商驱动抽出协议，写成标准子系统的传输驱动（I2C 桥写成 HID transport，单线 UART 写成 serdev），协议核心单独一份并带单元测试；电源生命周期按原厂。
- **规则**：
  - 参考的是另一台设备的配件实现 → 先确认协议和电源模型（主动心跳还是事件驱动），不同时只借协议解析，不借保活和恢复策略。
  - 枚举成功但没有按键 → 先查电气层（常开电源、总线电平），再查协议。
- **为什么**：同品类配件在不同设备上的协议可以完全不同。

## 5. 电源

### 休眠方式
- **默认做法**：s2idle（suspend-to-idle）：内核 `mem_sleep_default=s2idle`，systemd `SuspendState=freeze`。
- **规则**：
  - 显示还是借用固件画面，或者外设电源管理没做完 → 先禁止休眠（`sleep.conf.d` + 桌面空闲动作设为无）并登记技术债；按"真熄屏 → 外设电源管理 → 无线（PCIe 保留链路时不关电源域）→ 充电控制交接 → 传感器停流和电量计停轮询"的顺序做完再开启，不要先开休眠再逐个修。
  - 日志显示休眠一两秒就醒了 → 先用墙上时间或 `BOOTTIME − MONOTONIC` 复核；s2idle 要把多段 `Timekeeping suspended` 加起来；确认是真的早醒再找来源。
  - 确认是真的早醒 → 在 IPCC 和 glink 层临时加追踪找来源；休眠前停掉传感器数据流；避开开机后的通知期再测；不要屏蔽 IPCC。
  - 唤醒后某个外设不工作 → 逐个外设查 PM 回调。
  - 唤醒后黑屏 → 查显示的熄屏亮屏链路。
  - 按电源键后十几秒才挂起 → 查 logind 延迟锁（`ListInhibitors`），看谁持有到 `InhibitDelayMaxSec` 上限；不要调低上限掩盖。
  - 能挂起、能唤醒，但 SoC 从不进最深状态（例如 CX 不塌缩）→ Linux 侧的投票全为 0 也不能下结论，远端处理器用自己的通道投票（例如 `.prepare` 里发 IPC 的"投票时钟"，消费者在 probe 时 prepare 就成了常驻票）；拿原厂挂起时的同一组计数做参照，逐项找差异。
  - 某个"为省电"的上游改动导入后开始整机复位 → 它让系统第一次走进了以前没走过的路，潜伏的配置错误（例如缓存分片表里该预留的路被写成可借用）才显形；对照这颗芯片自己的原厂表和上游提交历史，不只看同族多数。
  - 挂起后立刻被唤醒 → 逐个看布防的唤醒中断：I²C 设备节点带 `wakeup-source` 时，I²C 核心会自动把它的数据中断设为唤醒源；"开盖才唤醒"的开关，只在入睡时盖子确实合着才布防。
  - 用配置关掉一个驱动做实验 → 设备树节点还在、没有驱动，sync_state 会挂起，内存频率可能被钉在最高档；要关设备就在设备树里关节点。
  - s2idle 功耗不达标，且早醒源都已归源 → 拔线做 deep 与 s2idle 的功耗对比，按数据决定。
- **为什么**：在已测过的几代高通平台上，远端处理器经 IPCC/glink 发来的消息会把 deep 休眠完整唤醒，而且不出现在唤醒记录里；s2idle 下非唤醒中断只让 CPU 短暂醒来再睡回去。新平台先测再定。单调时钟在休眠中不走，s2idle 一次休眠会被切成很多段。远端的投票和配置表由 Linux 编程、远端使用，现象在远端，原因可以在本端。
- **不适用**：没有这类远端处理器消息、deep 休眠成熟的平台，按功耗数据选择。
- **怎么测**：先 `pm_test` 逐级（freezer → devices → platform → processors → core）再真休眠；自动化用 RTC 相对时间唤醒；要在挂起中到点唤醒的恢复计时器用相对计时器加 `WakeSystem=yes`（这时它按包含挂起的时钟走；没有 `WakeSystem` 的单调计时器在挂起中停走），不用 `OnCalendar`（系统时间可能是错的）；物理唤醒（电源键、键盘、开盖）各测一次；插电和电池各测一次（调试线插着时永远是"插电"）；抓深睡里的最后日志可临时关 console_suspend，但决定性测量前恢复（它会让挂起时切换控制台、点亮面板，s2idle 立即退出）。
- **验收**：成功计数增加、墙上时长正确、启动 ID 不变、SoC 进入最深状态；唤醒后显示、触控、键盘、Wi-Fi、蓝牙、音频都能用；次数按要发现的故障率定。

### 电源键与合盖
- **默认做法**：电源键只有一个处理者（logind 或桌面二选一，另一个设为忽略）；休眠完成前短按设为无动作或保留关机对话框；休眠完成后短按为锁屏并休眠。合盖由 `SW_LID` 交给 logind；接外部电源时合盖只锁屏（`HandleLidSwitchExternalPower=lock`），用电池时挂起。
- **规则**：
  - 短按电源键直接关机 → 先查系统是否把设备判成了虚拟机。
  - 设置里没有电源键选项 → GNOME 对 tablet 机型隐藏它，可以把 Chassis 设为 convertible，同时核对它对睡眠延迟、蓝牙设备类别的副作用。
  - 需要桌面没有提供的电源键行为（例如只锁屏）→ 基于发行版源码包打最小补丁并登记退出条件，不 fork 核心组件，不加常驻服务轮询。
  - 插电合盖后屏幕过一会儿又亮 → 查是不是合盖发起了挂起、又被驱动拒绝（例如充电交接或"插电不睡"的保护）：GNOME 把失败的挂起当成一次唤醒，会重新点亮屏幕。改策略层（插电合盖只锁屏），不改驱动的拒绝。
  - 合盖后隔着盖子按键仍能点亮屏幕 → 查合盖时谁还在把键盘事件交给桌面：键盘驱动有没有按盖子状态停用，libinput 有没有把这块键盘和盖子开关配对。
- **为什么**：两个处理者同时响应电源键会冲突；桌面对机型的判断会改变很多默认行为；拒绝挂起和失败即唤醒各自都是按设计工作，错在插电时仍由合盖发起挂起，这也与原厂"插电不睡"一致。

### 充电
- **默认做法**：只读先行（电量计、充电状态、输入电压电流）；写入用白名单和限幅，未知充电源拒写；休眠时交接；私有快充复用社区实现。
- **规则**：
  - 通用 battmgr 在新 SoC 上读数不对 → 先查数据布局和电流符号 quirk；协议仍不兼容 → 写厂商私有通道的只读客户端。
  - 原装快充充电器在 5 V 下电流极低 → 说明需要认证和高压协商，复用社区实现；不要在 5 V 上反复做实验。
  - 要写充电参数 → 白名单、限幅、未知源拒写；休眠前交接，交接失败就拒绝休眠。
  - 设计休眠交接 → 交回的是"不需要 AP 维护也能正常充电"的配置（按充电源类型的限流，能固定的高压档先固定），而不是最低限流：否则插着快充合盖一夜基本不进电。快充期间电源仍要报告"已接电"。
  - 两条安全规则叠在一起（"交接失败就拒绝休眠"+"不向未知源写入"）→ 把它们代入最常见的状态核一遍：先按固件的语义确认枚举值（有的固件拔线后报 `Unknown`，意思是"当前没有可识别的电源"，不是"状态出错"）；确认没有电源时，没有东西需要交还，跳过交接、留给下一次插入的路径复位；读取失败和 `Unknown` 分开处理，读不到时不推断成拔线。
  - 测试充电功能 → 先确认电量和温度落在功能真正起作用的区间（快充、睡眠中充电在满电时看不出来）；测试前等电量用墙充，定时读新数值；Android 下用电脑 USB 慢充可能几小时后自动停充。
  - Linux 下无法净充电 → 文档写清楚，测试前设电量门（例如离开 Android 前 ≥ 40%）。
- **为什么**：快充协商常需要主机参与；标志位可以被强写而电流不变；AP 睡着以后没人维护的配置会落回固件的保守默认。
- **验收**：只看 15–30 分钟的电量和电压趋势、电流，不看标志位；插电睡眠、拔线睡眠各一次。

### 系统时间
- **默认做法**：墙上时间 = RTC 原始计数 + 操作系统自己保存的偏移。高通 PMIC 的 RTC 计数在原厂和主线读到的是同一个值（常从 1970 起算），原厂由一个时间守护进程把偏移存在自己的数据文件里。主线用上游 `rtc-pm8xxx` 已支持的 nvmem 偏移：在 PMIC 的 SDAM 里划出几个字节接到 RTC 的 `offset`，不改原始计数。
- **规则**：
  - 选 SDAM 单元 → 先对照原厂设备树里该 SDAM 的已用区域，再在原厂系统只读确认目标字节没被占用；设备树没声明不等于固件没用，没核实之前不部署。偏移能否跨异常复位保持取决于单元的保持性和复位类型，分别验证；保不住时靠联网校时兜底。
  - 想打开 RTC 写入（`allow-set-time`）→ 不要：改原始计数会让 Android 保存的偏移失去基准，破坏双系统的时间。两个系统各存各的偏移，共享原始计数。
  - 偏移方案落地之前的过渡 → 开机恢复上次保存的时间（fake-hwclock，oneshot 服务加 `RemainAfterExit=yes`）加 chrony；注意此时 RTC 仍在原始计数的时间域，绝对时间的唤醒闹钟永远不会到期，一律用相对时间。
  - 联网后仍不同步 → 分层检查证书时间、NTS 密钥交换、NTP 传输和选源：开机时间错误导致证书"尚未生效"时，用有次数上限的 `nocerttimecheck 1`；路由器劫持 NTP、认证源不通时，是否接受未认证时间（`authselectmode ignore`）是另一个决定，写明代价。偏移方案落地后撤掉为 RTC 加的过渡配置。
- **为什么**：PMIC RTC 在 Linux 侧通常不可写（写入被总线仲裁拒绝）；原厂开机日志里通常就有一行把系统时钟设成 1970 年附近的记录，说明原厂也只读原始计数。`-ENODEV` 这类返回值是驱动里的一个分支，翻译成硬件结论前先读到返回它的那一行代码。

### 调频与温控
- **默认做法**：核对传感器的量纲和校准后，温区、阈值和轮询间隔与原厂一致；频率以硬件计数器为准。
- **规则**：
  - 大核到不了标称最高频率 → 先读硬件计数器的实际频率（有 AMU 时 `cpuinfo_avg_freq`）和 `scaling_max_freq` 的轨迹：上限被压而内核冷却设备都在 state 0，首要嫌疑是固件经 SCMI 性能限制在压（在 SCMI 平台上用 limits 通知或 freq QoS 确认来源；Android 也受同一个上限），改调度器、改调速器都没用。
  - 跑分低于原厂 → 先核对缓存控制器（LLCC 一类）等驱动是否内建并工作、温控 trip 是否比原厂低，再怀疑调度器。
  - 想定一个比原厂更严的温度阈值 → 先量原厂在同负载下到多少度；比原厂更严的通用阈值只记为风险，不否决原厂同款设置。
- **为什么**：`scaling_cur_freq`、`time_in_state` 是 cpufreq 的请求值；单核满载时热点温度很快到固件门限，固件按温度给出上限。

### 看门狗
- **默认做法**：先做受控失喂测试，确认硬件看门狗真的会复位；没验证之前不依赖它恢复。无人值守测试的镜像内建硬件看门狗驱动，由 systemd 武装，作为硬挂时的最后一道回程。
- **规则**：systemd 默认在重启阶段打开看门狗（`RebootWatchdogSec` 默认 10 分钟），运行时看门狗默认关 → 两个阶段分别设：超时值不超过硬件上限，或者关掉；无人值守测试时按硬件上限武装（例如命令行 `systemd.watchdog_sec=`）。
- **为什么**：hypervisor 提供的看门狗可能喂狗时计数不变、失喂也不复位；没有看门狗兜底时，内核硬挂只能等人按键。

## 6. 无线

### Wi-Fi 监管域、功率与固件
- **默认做法**：监管设置要与实际使用地区一致：启动时按用户所在地区设定一次（不确定时用最保守的 world `00`），不在运行中切换；按原厂方式在启动时下发 SAR 功率上限；固件和 board 数据按原厂版本组合整套使用。
- **规则**：
  - 5 GHz 一个也扫不到 → 查驱动的频段范围计算（某些国家规则下会把 5 GHz 去掉）和 board 匹配日志。
  - 打算只换 board 文件做实验 → 先确认驱动是否优先读 `board-2.bin`；固件按版本组合整套换。
  - 能连上但几秒后断开 → 查发射功率是否超过原厂限值；对比原厂驱动启动时下发的命令，先于换固件。
  - 想按时区或用户位置在运行中自动改国家码 → 先不做；运行中改国家码可能引发 SMMU 故障、固件崩溃和驱动死锁，这是要修的缺陷，修好之前只在启动时设定。
  - 一次启动内想重新加载驱动 → 不做，重启后再测。
- **为什么**：国家码影响频段、功率和固件状态，变化路径在主线驱动里测试最少；原厂通过 SAR 上限避开了高功率下的问题。
- **验收**：5 GHz 80 MHz 连接后一段时间无断线；DHCP、ping、吞吐正常；休眠唤醒后能恢复。

### 蓝牙
- **默认做法**：地址从本机数据读出并持久保存，每次控制器初始化后（不是只在首次安装时）需要配置时经 MGMT 写入，再启动蓝牙服务；不写死在设备树；测试时两端同时抓 btsnoop。
- **规则**：
  - 公开镜像不能含本机地址 → 首启时由辅助程序写入，已配置时不改。
  - 手动执行成功、作为服务失败 → 先对比执行环境（标准输入输出、权限、命名空间），再 strace。
  - 重连失败 → 两端抓包；确认对端测试机的内核没有已知蓝牙缺陷。
- **验收**：配对、传输、音频或输入、重连、冷启动、与 Wi-Fi 共存。

## 7. 远端处理器外设

### 传感器
- **默认做法**：先查传感器挂在哪个远端处理器上（SLPI 还是 ADSP 的 sensor_pd）；用开源的 hexagonrpc + libssc + 带 SSC 支持的 iio-sensor-proxy；本机配置从 Android 只读导入，不进公开仓。
- **规则**：
  - 借用另一台设备的传感器路线 → 先确认处理器相同，补丁可以复用，启动方式不一定能。
  - 远端处理器在配置可读之前就自动启动 → 改为用户态在配置可读后启动一次。
  - 测试 → 每组在新启动上判断；导入本机配置时拒绝过期副本。
- **为什么**：传感器 PD 每次远端处理器启动只读一次配置。

### 相机
- **默认做法**：先确认上游或社区是否有该 SoC 的相机子系统；有就整组导入，用 libcamera 软件 ISP；没有就标为不支持。
- **规则**：
  - 测试脚本能取帧 → 继续验证应用入口（相机服务、PipeWire、应用）后才算可用。
  - GPU 渲染某种像素格式有缺陷 → 可以临时换格式绕过，登记技术债，GPU 修好后换回。
  - 执行器或传感器电压没有本机证据 → 不启用该部件，不猜档位。
  - 测试拍到的画面 → 属于用户隐私，用后删除。

### 视频硬解
- **默认做法**：上游驱动 + 本机签名固件 + 编成模块；发行版缺的 GStreamer 插件用原生 APT 补。
- **规则**：验收每种格式都做快、慢两种消费，并逐帧与软件解码对比；平台数据借用相邻 SoC 时，对照厂商的消息序列。

### 扬声器增益
- **默认做法**：首次出声用保守增益；产品增益单独决定；没有扬声器保护时提高增益有损坏风险，给出数值链和风险由用户决定。
- **规则**：
  - 怀疑增益 → 在已知安全的范围内直接测一个有区分度的点（例如安全上限），不要每次加一点；没有扬声器保护时，原厂在保护算法下用的增益不算安全测试点。
  - 对照原厂只发现一处差异 → 最先单变量验证它，不要因为"看起来只影响数据"就往后排。
  - UCM → 在没有保存 ALSA 状态的全新系统上验收。

## 8. 图形与应用

### GPU 用户态
- **默认做法**：发行版 Mesa 认识这颗 GPU（按完整 chip id）就用发行版的；否则自编固定版本，编译参数跟发行版一致，装到独立前缀，用 `/etc/ld.so.conf.d/` 里排在发行版路径之前的条目加编译期默认的驱动路径让它成为系统默认，卸载即回发行版。
- **规则**：
  - 只靠环境变量（`LD_LIBRARY_PATH`、`LIBGL_DRIVERS_PATH`）选中自编 Mesa → 不要：清空或重建环境的程序（设置里的渲染器探针、sudo、pkexec 启动的程序）会加载发行版 Mesa 并退回软件渲染。
  - 新 GPU 的 Mesa 有缺陷 → 先查上游 stable 和 main，按提交回移并登记技术债；上游没修时写最小修正并准备提交。
  - 性能远低于原厂 → 找一个能工作的参照驱动（原厂驱动、同代 GPU 的其他实现），对同一份着色器比较编译结果，把开放问题变成 diff；参照只用来定位，实现自己写、自己验证。
  - GTK 视频只在一种渲染器下测过 → GL 和 Vulkan 都要测。
- 详见 `../experience/gpu.md`。

### 沙箱应用与浏览器
- **默认做法**：浏览器用 deb 版；snap 应用的 GPU 用以原版 `mesa-2404` 完整内容为底、只替换 Mesa 库的提供者，首启自动连接。
- **规则**：
  - 官方镜像已经预置了某个 snap → 不要在构建期删除，首启 seeding 完成后再原生移除。
  - snap 自带应用有问题 → 先 `snap refresh` 看上游是否已修。
  - snap、AppArmor 相关的问题 → 设时间上限，不是首版必需就后移。
- 详见 `ubuntu.md`。

### Android 应用与虚拟机
- **默认做法**：Android 应用用 Waydroid 一类的容器；虚拟机在固件 hypervisor 占着 EL2 的平台上走该 hypervisor 的虚拟机管理接口，而不是普通 KVM。两者都是可选功能，不放进首版必需项。
- **规则**：
  - 容器 → 内核补齐 Binder/binderfs、legacy iptables 的各张表、两族策略路由、XFRM/PF_KEY，按实际镜像的网络脚本核对；CPU 不支持 AArch32 时选纯 ARM64 镜像；容器用自己的 Mesa，新 GPU 往往要先走软件渲染（见 `../experience/ubuntu-userspace.md`）。
  - 虚拟机 → `CPU: All CPU(s) started at EL1`、KVM 报 `HYP mode not available` 时，root 和解锁都不会交出 EL2；先在原厂系统上用原厂的虚拟机管理程序跑通一个最小客体作参照，再移植对应的 hypervisor 驱动和用户态 VMM。验收到客体执行、退出、内存回收为止，设备节点出现、创建调用成功都不算。
  - 同名接口、同一个 ioctl 号、同样的结构体大小 → 不代表 ABI 语义相同；固定权威头文件，按原厂成功的调用序列核对 flags、结构和错误码。
  - 遮蔽 hypervisor 节点（防止 systemd 判成虚拟机）→ 只遮用户态看到的那份，内核的设备树数据要留着，虚拟机管理驱动需要它。
- **为什么**：这类 hypervisor 由固件启动并常驻，Linux 只是它的一个客体；能不能跑虚拟机取决于它开放的管理接口，而不是 CPU 有没有虚拟化扩展。

## 9. 工程

### 内核基线
- **默认做法**：最新稳定版 + 明确来源的补丁；上游覆盖一项就删掉本地实现。
- **规则**：
  - 社区分支领先 → 默认从中按功能挑提交；只有地基相同、来源可追溯时才整体换到社区基线（见下面的"社区复用"），换了也要按缺行清单核对自己的净改动。
  - LTS 缺这个 SoC 的支持 → 用最新 stable，不硬回移。

### 内核换代与多设备共用内核
- **默认做法**：同 SoC 的几台设备共用一条内核主线，各自一个板级设备树和独立的交付；共同的修复只做一次。换代（例如跨大版本）时：首次上机前做"缺行清单"，首次受控 RAM 启动后比对开机日志，再做后续验收和持久安装。
- **规则**：
  - 缺行清单 → 把旧产品相对它的上游基线的净改动（不是提交标题清单），按功能逐项对到新树里，标明"上游已有等价实现""本地保留""主动淘汰""被误删"或"待确认"；设备树按节点和属性比对。逐行 diff 用来发现遗漏，不代替语义判断。冲突清理时最容易悄悄吞掉文件尾部或整段补丁。
  - 要删一个本地补丁、理由是"上游已经支持" → 先确认上游的等价物在这台设备的运行时条件下真的生效：例如上游按 SoC compatible 匹配，而 bootloader 把运行时的根 compatible 改写成了平台通用名，上游的匹配就落空，依赖它的电池、声卡会一起消失。
  - 首次受控 RAM 启动之后 → 先比对同一台机器新旧内核开机日志里的探测与服务差异（哪些驱动没 probe、哪些服务没起来），再做功能验收；验收覆盖用户可见项（电量与图标、声音、显示、触控、相机、挂起实睡时长与唤醒源、无线），截图亲自看。
  - 配置片段合并 → 后面的片段覆盖前面的；共用片段放在板级片段之前，否则共用片段里的 `=m` 会把板级要求内建的驱动降成模块。
  - 跨大版本 → 查新版本已知的回归和配套修复（例如 v7.3-rc2 合入的 `544d85de4dc2` 会丢掉 QRTR 服务公告，要配套带上修复 `743b5c86276b`，见 `../experience/kernel-and-resources.md`），对着同 SoC 社区的换代记录走一遍。
- **为什么**：换代时最常见的倒退不是新代码的问题，而是旧的本地修复在搬运中丢了，或者"上游已支持"的假设在本机不成立；开机日志的差异比功能测试更早、更全地暴露这类缺失。

### 社区复用
- **默认做法**：每个组件选一个主要跟踪来源；先比较两边的"地基"（设备树路线、资源管理方式、init、安装方式）。
- **规则**：
  - 地基相同、来源可追溯 → 可以换到社区基线，仍按缺行清单核对自己的净改动。
  - 地基不同 → 按功能系列整组导入（保留作者、来源提交和原有尾注），板级数值仍取本机，本机适配拆成小提交；不要逐行重新推导。
  - 社区"已支持" → 在本机验证差异和集成后才算通过。
  - 照搬原厂或社区的做法 → 搬它的语义，不只搬数值；原厂"能用"有时只是靠一个偶然的顺序。

### 接收社区贡献
- **默认做法**：每个版本审一次，能合就合，小问题合进来自己修，不等作者改；不该合的说明原因关掉。合并之后的组合（包括你自己摘取、适配的部分）按同一组检查验收。
- **规则**（贡献者和维护者同样适用）：
  - 一个 PR 一个主题，基于接收分支的最新提交，可以独立评审和回退；删掉已合入、被替代或无关的提交。旧基线上的 PR 先按 patch-id 去重，再按当前树的调用路径、配置和资源所有权判断它还有没有效果（例如保活修复已被现有机制覆盖、启用了 zswap 却没有交换空间）；一个功能只保留一个权威实现。
  - 标题、正文、"已修/已测"的声明，逐条能在最终 diff 里找到。
  - 按项目的真实发布方式构建（完整配置、设备树、匹配的模块、包与服务）。
  - 硬件边界：固定地址、硬件参数和共享代码的改动，给出原厂或上游依据，核对所有支持的变体（内存容量、屏型、外设有无）和现有消费者。固定在某个内存容量末端的保留区，会让另一种容量的机型开不了机。
  - 真机回测：冷启动；`dmesg` 没有新增 Oops、BUG、WARNING、hung task；挂起和唤醒；显示与触控生命周期；改动所涉子系统缺席或失败时不拖垮启动。范围随改动定，纯文档不要求真机。
  - 署名与来源：用贡献者自己的身份；导入保留原作者和尾注；AI 协助的提交如实写明实际使用的工具和模型，不能代人签署或声称测试。
  - 不越权：普通 PR 不分配 ABI 号、不改发布锁和校验值、不扩大权限。不带个人设备数据：默认日志里也不能打印蓝牙地址、序列号等。
  - 与项目范围无关或有法律、道德风险的内容不收。
- **为什么**：社区 PR 最常见的问题是署名缺项、声明与 diff 不符、一个 PR 混多个功能或基于过时分支；后果最重的是硬件边界漏查，而且常发生在维护者摘取适配之后。
- **配套**：仓库里放贡献说明、给贡献者 agent 读的规则文件和 PR 模板；托管平台的默认分支要指向当前发布线，否则新 PR 默认开在旧分支上。

### 打包与版本
- **默认做法**：按层拆包（见 `ubuntu.md`）；内核每次打包升 ABI 号；软件包版本号单调。
- **规则**：
  - 基础设备功能依赖了某个桌面组件的特定版本 → 拆开，桌面适配单独成包。
  - 要发布的版本号小于测试机上装过的内部版本 → 提高版本号；内部构建用 `~dev` 一类后缀。
  - 已发布的标签需要更正 → 发新版本，不移动标签。

### 固件分发
- **默认做法**：这是法律风险决策，由项目所有者决定。随项目分发时附逐文件清单（来源、路径、哈希），如实写明没有再分发许可、权利人提出异议即删除；本机唯一数据永远不进。
- **规则**：更稳妥的做法是让安装器从用户本机或允许下载的来源提取 → 先确认提取工具链完整可用，否则安装门槛过高。

### 构建环境
- **默认做法**：见 `build-environment.md`。
- **规则**：
  - 某个步骤超过 5 分钟 → 先分段计时找到大头，再决定优化什么。
  - 在 x86 上用全系统模拟构建 ARM64 根 → 改用原生 ARM64（例如 CI 的 arm64 runner）。
  - 日常迭代 → 在设备上装包，不重建整个根。
  - 自编发行版也有的大型用户态组件（Mesa 等）→ 编译参数跟发行版该包的实际参数一致（例如 Debian/Ubuntu 用 `-O2`）：偏离发行版参数就走上一条很少有人测的路径，已经出现过只在 `-O3` 下触发的编译器误编译。

### 首版门槛
- **默认做法**：别人能按文档构建、安装、使用；支持表只写真机通过的功能；不要求所有外设完成。

### 版本节奏
- **默认做法**：每个版本先写定范围和验收方式 → 开发 → 集中测试（需要用户参与的放到最后一次）→ 发布 → 清理 → 再开下一版。功能版是一组用户能明显感受到的能力；修复版（例如 x.y.1）攒一批已知问题的修复。
- **规则**：
  - 候选编号不断增加、分支未合并、长时间没有发版 → 停下来定范围、发版。
  - 只为一个小修复发版 → 不要，攒进下一个版本；严重回归是否单独发版由用户定。
  - 发布说明 → 按上一版标签到本版的提交逐条核对用户能感知的变化；"已知限制"只写本版新功能用户须知的限制，长期未支持的硬件留在支持表里，不每版重复。

### 何时放弃一条路线
- **默认做法**：新实验已经不再改变判断（同类失败第二次出现且没有新信息）；或一个单次实验已证明走不通；或维护成本明显超过收益、用户叫停。放弃时写进放弃记录，注明失败的前提条件和重新考虑需要什么证据。
- **规则**：
  - 宣布"不可行"之前 → 先读相关通用驱动的源码，确认不是某个具体参数（例如写入宽度）错了。
  - 下面这些路线在同类高通 ABL 设备的多个项目里被证明不划算或走不通；前提相同、又没有新证据时不要再走（前提不同的设备按各节的条件重新判断）：只改属性位切槽、B 槽装 Linux、recovery 落点、原厂内核上拼 RAM 探针、USB 串口作主通道、网络块设备作根、无 root 的用户命名空间构建根、构建期删除预置 snap、运行中切换 Wi-Fi 国家码、打开 PMIC RTC 写入、多媒体驱动一次性内建、无时间上限地深挖 snap/AppArmor。

### UEFI 引导层
- **默认做法**：作为可选的后续方向，不放进首版。它是不同产品目标（开机菜单、标准 ESP 启动）下的启动选择，不是其他硬件能力的前置条件。
- **规则**：
  - 评估时先确认：固件里是否嵌了不能再分发的原厂组件；它是否替换 boot（Android 更新会覆盖）；槽成功标记怎么处理；UEFI 退出时的硬件状态（显示、SMMU、时钟）和 ABL 不同，之前基于 ABL 交接状态的结论都要重测。结论不明确时只做一次只读的 RAM 验证。
  - 指望 UEFI 带来 KVM 或去掉 hypervisor → 不会：ABL 之前的高通固件和 hypervisor 都还在。
  - 设备自带的 UEFI 下载端点 → 不一定是标准 fastboot 协议（USB 接口类和命令帧都可能不同），主机工具能列出设备不等于协议能用。
  - 社区的 UEFI 方案里某个有用的做法（例如读原厂 bootloader 给出的硬件识别结果来选面板）→ 单独借鉴，不必为此引入 UEFI。
